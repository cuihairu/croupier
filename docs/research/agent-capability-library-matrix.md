## Why This Inventory (Overview)

The bugs exposed by agent testing and production incidents cluster in the **corners of in-house infrastructure**: a transport-layer JSON/proto layering error (the 19-function sync failure incident, fixed twice in 942e1bf4e/4a9a67cd6), five data races self-documented in comments (app.go:47-50, upstream.go:31-32, ops_server.go:42-44/410-414, tcp_local_listener.go:197-201) plus one fatal RWMutex misuse, three reconnect-backoff implementations behaving differently, and rate-limit windows going flaky on slow machines. The common shape of these bugs: **hand-rolled wheels re-implemented mature problem domains (backoff scheduling, concurrent shutdown, rate-limit boundaries) and then re-stepped on the pitfalls the industry already stepped on, inside their own implementations**.

But the inventory equally found that the agent's **protocol layer is not a wheel — it is a product contract** (framing/protocol header/MuxConn): all six language SDKs implement this wire protocol (`docs/architecture/sdk-wire-protocol.md`); replacing it equals rewriting every SDK. So the right output of this inventory is not "replace everything with libraries" but **hand "domain problems" to mature libraries (backoff/rate limiting/validation) while keeping "product contracts" in our own hands (protocol/session/scheduling semantics)**, plus cleaning up known internal defects in the in-house code.

## Decision Record (2026-10-07)

**What was decided**: all 16 conclusions of the matrix are endorsed along with the section-3 batch order; two open questions settled here — ① batch E's "wire it or remove the config item" either/or resolved to **wire it** (the `AgentTLSConfig` config promise already exists; a dead config item violates the boundary-honesty principle; TLS sits above TCP and below framing, so the six-language SDK wire protocol is unaffected — each SDK only needs a TLS dial option); ② batch order A→B→C→D→E→F, with D (kin-openapi differential) as the risk-gated batch — an excessive comparison diff halts D alone without blocking A–C.

**Why**: ① the three replacements (backoff / rate limiting / schema derivation) are all direct evidence of "domain problems hand-written, then industry pitfalls re-stepped" (slow-machine flake, thundering-herd risk, derivation corners), and every candidate is an official/ecosystem standard or already a dependency of this repo (zero new-adoption cost); ② the keeps are either product contracts (wire protocol/MuxConn; replacing = rewriting six SDKs) or have disqualified candidates (robfig/cron is unmaintained) or have no qualified candidate (process management/devcert); ③ the two additions (jsonschema validation, local gateway TLS) are both make-up work for "config/contract promised but implementation missing", incremental and non-breaking.

**Alternatives** (rejection reasons): replace everything (yamux/smux for MuxConn etc.) — mistaking request/response multiplexing for stream multiplexing, moving complexity elsewhere for a rewrite that also drags six SDKs, wiping out all production validation; keep everything as-is (execute no batches) — A/B's thundering-herd backoff and rate-limit flake are real failure shapes already recurring in production and on slow machines; ignoring them is the risk.

**Re-review hooks**: a batch-D comparison diff rate >5% or an undecidable item halts D and is written back here; yamux/smux candidates are re-evaluated if "single-connection bandwidth bottleneck / hundreds of concurrent streams" needs appear; koanf is introduced on demand once the config compatibility layer is fully retired.

## 2. Item-by-Item Argument

### 1. Reconnect/retry backoff [Replace (cenkalti/backoff/v5)]

**Why it is a problem**: three backoffs coexist in the same codebase — upstream reconnect is fixed 5s polling (no exponentiation, no jitter), registration sync is hand-written 200ms→2s doubling, and the OpenAPI provider retries linearly at i+1 seconds. Three inconsistent implementations are a maintenance burden in themselves, and fixed 5s polling carries a concrete failure-amplifier risk: when the server restarts, N agents redial simultaneously at the same 5s phase (no jitter against the thundering herd) — exactly the reconnect pressure behind past incidents like "dual-instance registry view split" and "cpp demo reconnect hang". The hand-written doubling has no ceiling jitter; under a long outage it plateaus at 2s and beats at a fixed rate.

**Why this library**: cenkalti/backoff is the de facto Go backoff standard (this repo's go.mod already carries v5 as an indirect dependency — zero new-adoption cost); NewExponentialBackOff gives the four knobs (initial interval/multiplier/max interval/randomization), and `NextBackOff()` + `ctx` covers all three existing scenarios. ~30k dependent repos, still releasing as of 2025-07, being packaged for Debian/Guix — liveness undisputed.

**Migration path** (low risk, cohesive interface):

1. `upstream.go`'s `reconnectLoop`: `backoff.NewExponentialBackOff` (InitialInterval=5s, Multiplier=1.5, MaxInterval=60s) + `backoff.WithContext` preserving ctx cancellation semantics; Reset on successful reconnect. The default randomization provides anti-herd jitter for free.
2. `upstream.go`'s `syncWithRetry`: same library replacing the hand-written doubling (InitialInterval=200ms, MaxInterval=2s; the existing ceiling semantics unchanged).
3. `openapi/provider.go:843-856` retry loop: linear i+1 seconds → `backoff.ConstantBackOff` first (behavior-equivalent); exponentiation evaluated separately later if wanted.
4. Tests only grow: keep the existing backoff cases; add "backoff sequence within the exponential upper bound" and "immediate exit on ctx cancellation".

**Risk**: the changed reconnect timing may break cases/ops scripts assuming "fixed 5s" — the migration PR greps out all hardcoded 5s assertions; `TestGoMigrations`-style smoke tests are unaffected.

### 2. Token-bucket rate limiting [Replace (golang.org/x/time/rate)]

**Why it is a problem**: `ratelimit/tokenbucket.go` is 73 lines of hand-written channel-based token bucket + 570 lines in `advanced.go`. This repo's `TestSlidingWindowWaitVariants` is known to flake repeatedly on slow machines (memory archive on file) — hand-written rate limiting's waiting semantics are timing-sensitive, direct evidence of "domain problems hand-written, industry pitfalls re-stepped". x/time/rate's Limiter keeps accounts on a monotonic clock rather than counting on a channel; the slow-machine wait-window drift shape cannot occur.

**Why this library**: golang.org/x is the official Go extension standard library — Google-maintained, perpetually active, BSD-3 with no licensing burden; the official Go wiki explicitly recommends it for token-bucket scenarios. `Limiter.WaitN/Reserve/AllowN` covers the openapi provider's three call shapes (blocking wait / reservation / direct admission). It does not cover sliding-window semantics — if `advanced.go` holds window logic (e.g. per-minute quotas), keep the window layer and swap only the bucket layer to x/time/rate; the two layers' responsibilities actually get clearer.

**Migration path**:

1. Inventory every caller of tokenbucket/advanced (openapi provider rate limiting, the ops surface) and list the current semantics matrix (burst, waiting, rejection).
2. Replace the bucket layer with `rate.NewLimiter(rate.Limit(rps), burst)`; waiting paths use `Wait(ctx)`, non-blocking paths `Allow()`.
3. New differential cases: with identical parameters, the first N admissions of old vs new must match (locks the behavioral contract); slow-machine flaky cases are converted to injection-point driven (aligning with the `prefer-injection-over-timing-tests` memory rule).
4. Keep the old implementation one release cycle under a deprecation comment before deleting.

**Risk**: behavioral differences concentrate in "boundary burst" shapes — the differential cases exist for exactly that; window semantics stay in the original layer, so the externally observable rhythm is unaffected.

### 3. OpenAPI schema derivation [Replace (after differential; getkin/kin-openapi)]

**Why it is a problem**: 207+155 hand-written lines derive the schema→function-signature mapping for 3.0.3 specs. OpenAPI's corners (allOf/oneOf composition, nullable, recursive $ref, default vs example precedence) cannot be fully covered by hand; the diversity of game-side specs is uncontrollable, and each new game onboarded may add a derivation bug. kin-openapi is **already** a dependency of this repo's go.mod (in use server-side; v0.137/v0.144 in the local cache), supports 3.0/3.1/3.2, and responded fast to the 2025 CVE (CVE-2025-30153 patch released).

**Why "after differential"**: this is not a pure internal implementation swap — the derivation result directly determines the function contract (inputSchema) registered to the platform, and behavior changes propagate to UI form generation and SDK validation. A comparison corpus must come first: collect the specs for all existing providers.yaml, run both implementations side by side, and adjudicate every diff by hand (old-right/new-wrong → fix the new implementation; old-wrong/new-right → record as a fix); switch only when the comparison is fully green.

**Migration path**: build the comparison corpus (snapshot existing specs into testdata) → rewrite input_schema derivation on the kin-openapi parsing layer → differential comparison → switch → delete the old derivation code. validator.go's business validation (platform constraints) stays; only the "spec parsing + schema traversal" layer is replaced.

### 4. JSON Schema validation [Add (santhosh-tekuri/jsonschema/v6)]

**Why it is missing**: the agent passes provider-returned InvokeResponse data straight through to server/web with no schema-level validation; the proto/JSON layering violations (`mux_conn.go:193,422` stuffing `{"error":...}` JSON strings into proto payloads) show that boundary validation of structured output was absent from the start — one root cause of the 19-function sync incident was error-shaped data entering the normal data channel. Once OpenAPI 3.1 support lands (#3), response schema validation has an authoritative source, and adding it closes the loop.

**Why this library**: v6 is the only actively maintained Go implementation covering drafts 4–2020-12 (gojsonschema stopped at draft-07 and is effectively dead), adopted in production by oapi-codegen, already in this repo's go.mod (in use server-side), Apache-2.0. It shares lineage with kin-openapi v0.136+'s internals (kin's 3.1 support is built on it), so the combination adds no conceptual cost.

**Migration path**: InvokeResponse gets schema validation (enabled when a response schema exists, skipped otherwise — compatible with existing providers) → validation failures go through the existing error-reporting channel (never silently swallowed) → new positive/negative cases.

### 5. Local gateway TLS [Add (wiring, not a library)]

The `AgentTLSConfig` config surface exists (root.go:124-131) but `tcp_local_listener.go` consumes only Address/RecvTimeout/SendTimeout — the config item is dead; users can set it with no effect. That is "config promise vs implementation mismatch", and the boundary-honesty principle requires either wiring it or explicitly removing the config item. The implementation needs only stdlib crypto/tls (the outbound direction already uses the same pattern; client.go:165-196 can be copied). The either/or: wire it (recommended — plaintext SDK↔Agent local TCP on shared hosts is a real exposure), or delete the field from the config struct and note the boundary in the docs. **Wiring is recommended**, because the frame format is unaffected (TLS sits above TCP, below framing), and the six-language SDKs only need a TLS dial option.

### 6. TCP framing + protocol header [Keep]

50 lines of framing + 296 lines of protocol header look like "a wheel" but are a **product contract**: the six language SDKs (go/python/java/js/cpp/csharp) each implement the same wire protocol, and `docs/architecture/sdk-wire-protocol.md` is its specification. No replacement candidate exists — any third-party framing (gRPC framing, msgpack-rpc, etc.) is a protocol change costing a full SDK rewrite plus a compatibility window, for negative benefit (the current protocol is simple and proven in six languages). Keep; and the historical bug here (19-sync) was fixed in the layering semantics, not the frame format itself.

### 7. MuxConn bidirectional multiplexing [Keep (candidates on record)]

yamux (hashicorp, libp2p default, 0.1.2 active) and smux (xtaci, v1.5.x active) are both qualified and mature. **Still keep**, because MuxConn is not stream multiplexing — it is **request/response semantics** multiplexing: a pending map keyed by reqID, a control lane with 1 worker that never rejects, and a business lane with a bounded queue that answers busy frames under saturation to trigger the peer's failover — this semantics is deeply coupled to the GM invocation model of "server broadcast / agent unicast / failover". yamux/smux provide a stream abstraction; adopting them means building another request/response correlation layer on top of streams — rewriting MuxConn's complexity somewhere else, plus syncing six SDKs. All production validation (converged after the 19-sync incident) would be wiped and redone. Candidates on record: if "single-connection bandwidth bottleneck" or "hundreds of concurrent streams" needs appear, re-evaluate smux v2 as the base. Incidental cleanup: delete the hand-written `errorAs` at `mux_conn.go:44-54` and use `errors.As` directly.

### 8. Load balancing FNV sticky hash [Keep]

70 lines of FNV-1a modulo instance selection. Consistent-hash libraries (buraksezer/consistent etc.) solve "mass key migration on dynamic node-pool scaling"; the agent scenario is **a handful of instances of one game service** (the registry indexes by `(game_id, function_id)`), so stickiness is enough and migration minimization is unnecessary. Swapping a library here is a cannon for mosquitoes, plus a new dependency. The 30s health window + degrade-on-all-stale semantics are kept.

### 9. crontab/systemd timer parsing [Keep]

robfig/cron/v3 is **disqualified** by the rule: zero releases after v3.0.1 (2020), 50+ open PRs backlogged, community forks already appearing. And the requirement, examined closely: the agent only does **read-only enumeration for display** (reading /etc/crontab, /etc/cron.d, and the systemd timer list for the ops surface), not scheduling execution — it depends on field splitting, not on the parser's scheduling correctness. The 237-line in-house parser covers exactly "loose parsing for display"; adopting a dead-project library would just bind its CVE risk. If scheduling semantics like "next trigger time of an expression" are ever needed, evaluate an active fork or systemd's native `NextElapse` (via D-Bus; availability under LXC to be discussed then).

### 10. YAML config compatibility layer [Keep (shrink only, never grow)]

koanf v2 is active (MIT, modular, light dependencies); viper is active but heavy. **Do not adopt**, because the 390-line compatibility layer's body is not "YAML parsing" (yaml.v3 already does that) but **business rules** — the dual-read mapping of PascalCase/snake_case legacy spellings (four UnmarshalYAML layers in root.go). koanf ships none of those rules; after adoption you would write the same mapping code — a shell swap, not a brain swap. The real governance path is already fixed in CLAUDE.md's config contract: **new keys are always canonical lowerCamelCase; the compatibility layer shrinks only, never grows**; once legacy keys die out naturally, delete the layer wholesale. If a modern config layer (layering/env vars/file hot-reload) is wanted then, koanf is the first candidate at that time (on record).

### 11-14. Logging / TLS+devcert / process management / HTTP client [Keep]

- **Logging**: slog (stdlib) + lumberjack is already the Go ecosystem's standard combination; no action.
- **TLS/devcert**: stdlib crypto/tls for outbound is the right answer; the 227-line devcert self-signed CA is a developer-experience component, and mkcert-class tools are CLIs that cannot be embedded as libraries — no qualified replacement.
- **Process management**: Go has no dominant process-management library; OpsServer's real defects (AutoRestart `time.Sleep` under lock, no process-tree termination, output not demultiplexed) are **bugs fixable within the in-house code** — listed in the "keep + internal defect list" and fixed in normal iterations; not a reason to swap libraries.
- **HTTP client**: the provider's complexity is the spec→HTTP semantics mapping (the 1115-line body), not HTTP itself — nothing in net/http that resty/req would improve. The only thing worth replacing is the retry loop's linear backoff, handled along with #1's backoff migration.

### 15. Session/registry double abstraction [Keep + internal convergence]

`internal/agent/provider_session.go` (210 lines) and `internal/transport/session/*` (378 lines) overlap functionally, two sets coexisting. This is not a library-swap question but **internal convergence**: designate one as standard (transport/session is the more general one; the agentlocal registry was thought to depend on it), migrate and merge the other, then delete. Listed in the internal defect list, handled in an independent PR (mind the boundary constraints from the `registry import cycle` memory).

**Execution ruling (at F's landing, 2026-10-07)**: verification before landing found `internal/transport/session` has zero consumers repo-wide — no imports from production code or out-of-package tests (the original text "the agentlocal registry already depends on it" had drifted from reality; agentlocal carries its own `ProviderSession` struct definition). The convergence direction flipped to **keep the live one, delete the dead one**: `agent/provider_session.go` is the implementation actually wired into `tcp_local_listener`/app and validated in production; `transport/session/*` is a parallel abstraction with no production mileage — migrating live code onto a zero-validation abstraction is pure risk for no benefit. Deleted wholesale (including its in-package tests); `provider_session.go` is now the sole session abstraction.

### 16. Serialization layering violations [Keep + close out with #4]

The official protobuf runtime is the right answer. The two JSON-into-proto-payload layering points (`mux_conn.go:193,422`, `local_handler.go:422,509-519`) are established conventions (the six language SDKs already align to this shape) and cannot be changed unilaterally — the close-out is #4's schema validation intercepting illegal shapes at the boundary; the protocol itself does not move.
