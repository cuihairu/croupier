# Crash Snapshot and Cross-Language Capture Survey

## Status

- Status: survey archive (2026-10-08, companion to Agent Supervisor #67 "survey first, decide later"; this document surveys only, it implements nothing). **The §6 light + medium tier decision items landed with the S3 delivery (2026-10-10, see [agent-supervisor-design.md](../design/agent-supervisor-design.md) §9)**
- Date: 2026-10-08
- Scope: viable paths to obtain memory snapshots when supervised processes crash — ① per-language native mechanisms (Go/Python/Node/JVM); ② an OS-level language-agnostic capture layer (core_pattern/systemd-coredump, Windows WER, Crashpad/Breakpad); ③ the language-dependence of the parsing layer; ④ comparison and a tiered plan recommendation + decidable items
- Conclusion at a glance: **no single application-level tool covers everything**; the evidence-backed combination is "an OS-level capture layer with zero integration (Linux core_pattern pipe / Windows WER LocalDumps) + language-native mechanisms for lightweight profiling + a per-language parsing layer". A Croupier-specific lever: supervised processes are spawned by the agent (`ManagedProcesses` configures command/env), so **language-native switches can be injected at spawn time** — the lightweight tier is significantly more feasible here than in the general case
- Related: [Agent Supervisor design profile](../design/agent-supervisor-design.md) §8 S3 (snapshot plan pending this document's decision, then merged)

## 1. Problem Definition

The game-server processes supervised by the Supervisor are written in different languages (Go/C++/Python/Node/JVM are all possible). Crash triage needs memory snapshots, but snapshot **capture** and **parsing** are two different things: the capture layer can be language-agnostic (the OS naturally owns all of a process's memory at termination), while the parsing layer is necessarily language-dependent (symbol tables, runtime object layouts). This survey proceeds along those two layers.

## 3. OS-Level Common Capture Layer (Language-Agnostic)

### 3.1 Linux: core dumps / core_pattern pipes / systemd-coredump

- A core dump is "an image of the process's memory at termination", naturally language-agnostic; `RLIMIT_CORE` caps its size, but **core_pattern pipe mode is not subject to that limit**; when `/proc/sys/kernel/core_pattern` starts with `|`, the dump is piped via stdin to a user-space program (running as root in the initial namespace, Linux 2.6.19+) — [core(5)](https://man7.org/linux/man-pages/man5/core.5.html).
- systemd-coredump takes over core_pattern via `/usr/lib/sysctl.d/50-coredump.conf`: the journal records a summary + backtrace, the core image is stored under `/var/lib/systemd/coredump/` (.zst compressed, auto-deleted after days), and `ProcessSizeMax`/`ExternalSizeMax` default to **32G** on 64-bit (767M limit inside the journal); `coredumpctl list/debug` hands the dump straight to gdb — [systemd-coredump(8)](https://manpages.ubuntu.com/manpages/noble/en/man8/systemd-coredump.8.html) · [coredump.conf(5)](https://manpages.ubuntu.com/manpages/noble/en/man5/coredump.conf.5.html).
- This route **covers processes in any language with zero integration**; Breakpad itself ships a `core_handler` (hooked into the core_pattern pipe to produce a system-wide minidump) as the "pipe → minidump" precedent — [linux_core_handler](https://github.com/google/breakpad/blob/main/docs/linux_core_handler.md).

### 3.2 Windows: WER LocalDumps

- Registry `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps` (global + per-application override subkeys): `DumpType` 1=Mini (default)/2=Full/0=Custom (`CustomDumpFlags`), `DumpFolder` defaults to `%LOCALAPPDATA%\CrashDumps`, `DumpCount` defaults to 10; **not enabled by default** — an administrator must write the registry; the source notes "apps that do their own custom crash reporting are not supported by this feature" — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps).

### 3.3 macOS

Crash reports are collected via the Xcode Crashes organizer / device transfers; jetsam (kill on high memory) is a separate report type — [Apple docs](https://developer.apple.com/documentation/xcode/diagnosing-issues-using-crash-reports-and-device-logs). The `~/Library/Logs/DiagnosticReports` path and the `diagnose` tool could not be verified from fetchable official pages (marked unverified). Server deployments are Linux-first; macOS is listed as a non-target.

### 3.4 Crashpad / Breakpad (Application-Level Cross-Platform Collectors)

- **Crashpad**: the handler is a separate process; the client library is linked into the executable module at compile time; on crash the process is suspended and the handler generates the snapshot (modules/registers/stack memory/OS state) and writes a minidump; the design motive is "the crashed process's state is untrustworthy, so run as little code inside it as possible". Platform status from status.md: macOS/Windows/Linux/Android/Fuchsia clients complete, iOS in development — [README](https://chromium.googlesource.com/crashpad/crashpad/+/main/README.md) · [overview_design](https://chromium.googlesource.com/crashpad/crashpad/+/main/doc/overview_design.md) · [status](https://chromium.googlesource.com/crashpad/crashpad/+/main/doc/status.md). **Language-agnosticism has limits**: the snapshot contents are OS-level entities (independent of implementation language), but the client is a compile-time C++ integration (sentry-native likewise requires C++17 and ships crashpad_handler with the program) — [sentry-native](https://github.com/getsentry/sentry-native).
- **Breakpad**: no official deprecation statement found (the repo still had commits as of 2026-10); Crashpad is its successor within Chromium. On Linux it installs signal handlers inside the crashing process by default to write dumps, and the official docs warn themselves that "writing a minidump inside the crashing process is unsafe" — [getting_started](https://chromium.googlesource.com/breakpad/breakpad/+/master/docs/getting_started_with_breakpad.md).

## 4. The Parsing Layer (Language-Dependent)

- The minidump is a Windows user-mode format, "a useful subset of a crash dump, small enough to send over the network"; the client writes only "uninterpreted byte streams" (no function names/line numbers). Symbol chain: `dump_syms` (reads DWARF/PDB, must be produced before stripping) → `.sym` → `minidump_stackwalk` symbolizes — [minidump-files](https://learn.microsoft.com/en-us/windows/win32/debug/minidump-files) · [getting_started](https://chromium.googlesource.com/breakpad/breakpad/+/master/docs/getting_started_with_breakpad.md) · [Chromium decoding guide](https://www.chromium.org/developers/decoding-crash-dumps/).
- A modern alternative: Mozilla's rust-minidump (minidump-stackwalk/breakpad-symbols), whose README self-describes as "heavily modeled after Google Breakpad" — [rust-minidump](https://github.com/rust-minidump/rust-minidump).
- **Go**: the compiler emits DWARF by default ([cmd/compile](https://pkg.go.dev/cmd/compile)), so it could in theory feed dump_syms; but **no official Breakpad/Crashpad Go client/support documentation was found — no mature precedent verified**.
- **Java/Python**: a minidump stores only raw stack bytes + registers; language-level stacks require language-side tooling (`jstack` output carries full class/method/line info) — [jstack](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jstack.html). For managed languages the value of an OS dump is mainly registers/native frames and memory contents; language stacks still need the native tools in parallel.

## 5. Comparison Table

| Option                       | Language coverage                           | Platforms                    | Integration cost                           | Overhead                                  | Artifact                            | Parsing tools                    |
| ---------------------------- | ------------------------------------------- | ---------------------------- | ------------------------------------------ | ----------------------------------------- | ----------------------------------- | -------------------------------- |
| Language-native (pprof etc.) | One language                                | Whatever the runtime runs on | Low (inject env/flags at spawn)            | Low (sampled) to high (jcmd full GC)      | pprof/hprof/heapsnapshot            | Each language's toolchain        |
| core_pattern pipe            | Any (zero integration)                      | Linux                        | Low (a handler script/program)             | Full memory snapshot, large               | core or minidump (via core_handler) | gdb / minidump toolchain         |
| systemd-coredump             | Any                                         | Linux (systemd)              | Very low (system default)                  | 32G-scale reservation, compressed on disk | core (.zst)                         | coredumpctl → gdb                |
| WER LocalDumps               | Any user-mode process                       | Windows                      | Very low (registry)                        | Per-app configurable dump type            | minidump/full                       | WinDbg                           |
| Crashpad/Breakpad            | OS-level common; client needs C++ embedding | Win/macOS/Linux/Android      | High (source/build + handler distribution) | Suspend → snapshot, low intrusion         | minidump(+extensions)               | minidump_stackwalk/rust-minidump |

## 6. Tiered Plan Recommendation

**Precondition fact**: the croupier agent's supervised processes are spawned by the agent (`ManagedProcesses`: command/args/env), and **the agent controls the process's launch environment** — this is the key lever that makes the language-native tier feasible in Croupier's scenario (impossible in the general case).

| Tier   | Plan                                                                                                                                                                                                                                                                                                                                                                 | Fit                                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Light  | **Spawn-injected language-native switches** (per-process snapshot profile): Go → `GOTRACEBACK=crash` + a pprof endpoint; Node → `--heapsnapshot-signal`/`--report-on-fatalerror` (with `--report-exclude-env`); Python → `PYTHONFAULTHANDLER=1` (stacks) + tracemalloc on demand; JVM → `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<agent-managed directory>` | Default tier: low overhead, small artifacts, downloadable directly from the agent panel                           |
| Medium | **OS-level takeover as the fallback**: on Linux write a core_pattern pipe handler (or accept the host's systemd-coredump as-is); on Windows register WER LocalDumps per-app; the agent scans dump artifact directories for panel listing + download                                                                                                                  | Ground truth fallback for crashes in any language; large and sensitive, off by default / allowlisted              |
| Heavy  | Crashpad/Breakpad C++ embedding + the minidump symbol chain                                                                                                                                                                                                                                                                                                          | Only if there is a C++ game server needing a unified cross-platform minidump; no such demand today, not chartered |

**Recommended combination**: light (spawn injection) as default + medium (Linux core_pattern fallback) as an optional switch; Crashpad not introduced. Supporting facts: spawn control (code fact), core(5) pipe semantics covering everything with zero integration, native-mechanism overhead data (§2), and Crashpad integration cost with unverified Go support (§3.4/§4).

## 7. Sensitive Data and Production Discipline

- **A full dump/core/heapsnapshot contains the process memory in plaintext** (credentials, keys, PII are all in memory); Node's Diagnostic Report embeds **environment variables** by default (often containing secrets) and requires an explicit `--report-exclude-env` ([nodejs report](https://nodejs.org/api/report.html)); systemd-coredump's official docs likewise warn it contains all memory and is sensitive data.
- Recommended production discipline: snapshots off by default, enabled per-process allowlist; tightened ACLs on the artifact directory + a retention cap (systemd-coredump's auto-expiry is a reference); panel downloads gated by an ops permission bit with audit logging; artifact size quotas (discard on breach and log an event, to keep disks from filling).

## 8. Decidable Items

1. **Starting tier**: recommend "light = spawn injection (default) + medium = core_pattern fallback (optional)", rejecting a Crashpad/Breakpad charter (C++ integration cost vs. no C++ server demand today; no mature Go support precedent). **Approved as "follow the survey's tiered plan"** (recorded when the agent-supervisor design profile was filed, 2026-10-09).
2. **Light tier's config shape**: `ManagedProcesses[x].snapshotProfile: none|go|node|python|jvm` (explicit declaration, no language auto-detection — a misjudgment's cost is an ineffective injection or a polluted process environment). **Decided (2026-10-10, user-delegated): agreed, lands with the #67 S3 batch**. **Landed (2026-10-10)**: spawn injection (go/python/jvm env, node argv prepending, profile precedence) + `snapshotDir` (default `logs/snapshots`, 0700) + detect_down artifact registration.
3. **Medium tier's host prerequisite**: core_pattern is a host-global resource (root sysctl); changing it on a host running multiple game servers has blast radius beyond the agent. **Decided (2026-10-10, user-delegated): the agent gives read-only hints** — scan the host's current state (whether core_pattern pipe mode is on) + show the suggested command in the panel/logs for ops to copy in one click; the agent does not write host config directly (permission/security boundary, low-stakes in both teaching and production). **Landed (2026-10-10)**: read-only scan of `/proc/sys/kernel/core_pattern`; when not in pipe mode and any process enables the light tier, emit a single `snapshot_hint` host-level event (sync.Once against spam).
4. **Retention/quota/download permissions**: suggest 72h retention, a 2GiB per-process directory quota, downloads requiring `ops:operate` + audit; numbers are tunable. **Still pending decision** (outside this authorization's scope).
