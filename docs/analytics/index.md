# Analytics overview

> **Product boundary/status correction, 2026-10-29:** built-in shared core operations metrics, external professional analytics. Existing screens/models/pipelines are not end-to-end metric acceptance. Retention computation, source consistency and aggregate semantics still have gaps. See [scope, source evidence and delivery plan](./core-and-external). Metric groups below are a catalog, not a statement that all are implemented.

The analytics stack supports game behavior, retention, revenue, and warehouse reporting. Queries converge in the Analytics console; ingestion and storage are intentionally separated from the control plane.

## Pipelines

| Pipeline             | Source                   | Path                                                                             | Best suited for                                                                                      |
| -------------------- | ------------------------ | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| ClickHouse pipeline  | Game clients and servers | HMAC-authenticated `ingest` -> Redis Streams -> `analytics-worker` -> ClickHouse | High-volume events, warehouse detail, and pre-aggregated reports.                                    |
| Server GORM          | Server business models   | Per-game relational tables                                                       | Business-entity joins and moderate-volume overview, retention, behavior, payment, and level reports. |
| OpenTelemetry bridge | Server telemetry         | In-process bridge -> Redis Streams -> ClickHouse pipeline                        | Server-side automatic events without game-client changes.                                            |

### Batch validation and retry semantics

- Ingest validates the whole batch before publishing anything (DATA-016): an invalid item returns `400` with `details.index` and enqueues nothing.
- A publish failure mid-batch returns `500 queue_write_failed` with `details.enqueued` / `details.failed_index` / `details.total` (DATA-017): items before the failure are already in the stream and are disclosed, not hidden behind a bare batch-level error.
- Retry contract: re-submit the same batch unchanged. Events without a producer `event_id` get a deterministic UUIDv5 derived from the payload fingerprint in the worker (`internal/analytics/worker/worker_insert.go`, `deriveEventID`), so re-submission and worker redelivery collapse onto the same ClickHouse natural key instead of inserting random new ids. A producer-supplied valid UUID `event_id` is honored as-is.
- Amount precision (DATA-018): `amount_cents` must be a positive integer within the uint64 range. Ingest decodes JSON numbers with `UseNumber` and parses digit-for-digit — fractional, negative and oversized values are rejected `400` with the item index; the worker parses the amount the same way and dead-letters a bad row with a reason instead of truncating through float64.
- Retry retention (DATA-019): failed messages requeue into the **source stream without any retention cap of their own** — source-stream trimming (e.g. `ANALYTICS_REDIS_MAXLEN`) belongs to the publisher's configuration. A retry copy can no longer evict unread backlog entries once the backlog exceeds the old 1000-entry cap; retry volume is bounded by `retry_count` (dead-lettered after `maxPendingRetries`).
- Aggregate recovery (DATA-020): every touched minute/day carries a **durable flush marker** in Redis (`ANALYTICS_AGG_DIRTY_SET`), so a crash after the raw event was ACKed but before the aggregate row landed still leaves a flush obligation after restart. When a best-effort HLL write fails, a separate rebuild marker (`ANALYTICS_AGG_REBUILD_SET`) makes the next flush re-derive that HLL from the persisted `analytics.events` rows (HLL union is idempotent). A rebuild failure keeps the marker and does not persist a false zero; a healthy HLL write incurs no rebuild query.
- Daily revenue recomputable after payment ACK (DATA-021): every payment flush advances a **durable cumulative progress** hash in Redis (`ANALYTICS_REV_PROGRESS_SET`, per day/game/env the fields `<revKey>:rev/:ref/:fail` plus a `:ver` version) inside one atomic Lua script that also writes a per-message seen marker (`SET NX`, 7d TTL) — all before the message is ACKed. A crash after the payment Send+XACK but before the `daily_revenue` insert therefore leaves the owed cumulative total and a dirty marker (`r:` prefix in `ANALYTICS_AGG_DIRTY_SET`) in Redis; the restarted worker restores the total at startup and the next flush writes the **absolute cumulative row** under a strictly monotonic Redis-INCR version (seeded above the legacy wall-clock versions on first advance), so ReplacingMergeTree FINAL collapses replays — a flush re-run after a crash between Send and marker clear rewrites the same total, never an increment on top of it, and new payments arriving after a restart fold into the restored total. A failed advance leaves the source messages pending for reclaim, and the seen-marker dedup keeps already-advanced messages out of the retry. Boundaries: currency is still ignored and payment status semantics are unchanged — the revenue/status caliber remains DATA-004; a redelivery after the advance failed re-appends the payment detail row (a visible duplication in `analytics.payments`, the same exposure the crash window between Send and ACK always had — corrupting `daily_revenue` would be strictly worse); the cumulative totals idle-expire after 180 days and seen markers after 7 days (deliberately far beyond the 5-minute reclaim idle), so a redelivery older than the marker TTL could advance twice — that TTL is the Redis-growth bound; a corrupt progress hash (fields gone, marker left) is not restored as zeros and stays inert with a warning.
- Pipeline alert recovery (DATA-022): `event_stream_stalled` / `event_volume_drop` alerts close only on **positive evidence** — a scope row actually read in the current round that satisfies the recovery rule. A scope missing from the discovery window (fully silent = the very stall being alerted), a failed query, or a partially read result set is treated as unknown and keeps the alert firing (`events_query_failed` marks the unknown round separately). Recent and baseline rates are each divided by their own window length, so a non-default window pair does not skew the comparison.
- Consumer group initialization (DATA-023): a freshly created group starts at `WORKER_GROUP_START` — default `0`, so a worker started after the first inbound events consumes the retained backlog; `$` opts into latest-only. An **existing group is never repositioned at startup**: the Redis-native cursor keeps the consumption position across restarts and a stale application checkpoint cannot replay ACKed data. The persisted checkpoint is applied only when creating a group (resume after Redis lost the group) or through the explicit `WORKER_GROUP_RESET=true` operator reset. Group creation failures are logged, never silently discarded; a `BUSYGROUP` race against another worker keeps that worker's cursor.
- Window-wide behavior aggregation (DATA-024): summary, heatmap, adoption breakdown, funnel, paths and level/episode/map reports aggregate the **entire query window** by paging through every matching event, trusting the model's authoritative `count` to know when a type is exhausted (requested page sizes are re-normalized by `ListEvents`). Windows larger than the aggregation bound (`maxWindowEvents`, 50000) return a bounded sample and disclose it in the response `sample` object (`totalEvents`/`scannedEvents`/`sampled`/`coverage`), so a partial read is never presented as complete; the paged events endpoint keeps its own page-size contract.
- Realtime metric sources (DATA-025): `onlineUsers` counts **distinct users** with a `heartbeat`, `session_start` or dotted `session.start` event inside the 15-minute realtime window, and `activeSessions` counts `session_start`/`session.start` events in the same window. Business events (`login`, `purchase`, ...) feed throughput (`eventsPerMinute`, all behavior events / 15 minutes) but no longer inflate online or session counts. The `/analytics/realtime` response includes a `source` object naming each signal and the window length, and the realtime online series uses the same liveness events. Boundary: there is no player-session/heartbeat table, so "online" is an activity liveness proxy derived from analytics events, not a count of live sockets; a user with no liveness event in the window is offline by this definition even if still connected.
- Realtime series bucketing (DATA-026): `/analytics/realtime/series` reads the whole requested window in **one** bounded query (`maxRealtimeBucketRows`, 100000) and buckets rows in Go; database round trips are decoupled from the bucket count (the old code issued two queries per bucket — up to 2880 at the longest supported window). Every bucket is materialised, including empty ones, and a row on a bucket boundary contributes to exactly one bucket. Events beyond the row cap are disclosed in the response `sample` object (`scannedEvents`/`sampled`/`coverage`), never presented as a complete window.
- Overview WAU and retention read chain (DATA-027): `/analytics/overview` returns a real rolling `wau` (the same distinct-user measure as DAU/MAU over 7 days) and `retentionD1/D7/D30` computed from distinct (day, user) behavior-activity pairs — the retention cohort table has no production writer, so behavior events are the only source. A cohort day counts once day+N has **fully elapsed** inside the queried window (a date-only end covers its whole day; a "now" end yields only fully elapsed return days), and the value is pooled retained users / pooled cohort users across mature days. Each figure carries `status` (`ok` | `pending` | `no_source`), `cohorts` (mature cohort days pooled), `sampled` (pair scan truncated at `maxRetentionPairRows`) and `value` (null unless `ok`; 0 is a real zero). The web overview maps a number only for `ok` — a real zero renders 0%, `pending` renders "Pending maturity" and `no_source` keeps the `-` placeholder; Mobile reads the same status payloads through the analytics facade. Boundary: retention is an activity-pair approximation, not the cohort-table definition pending the DATA-001 metric decision.
- Peak online from the observation window (DATA-028): `/analytics/overview` returns `peakOnline` — per-day peaks taken as the interval maximum of the same online series the realtime screen plots (distinct liveness users per bucket, half-open buckets so a boundary event lands in exactly one bucket). Days follow the **declared UTC boundary** the rest of the relational overview trends use (`DATE(occurred_at)`), and the `meta` object discloses `timezone`, `granularitySeconds` (1-minute buckets), `sampled` (row scan truncated at `maxPeakOnlineRows`), `totalDays` / `coveredDays` and `coveredFrom` / `coveredTo`. A day counts as observed when **any** event row falls on it: a day with rows but no liveness events has a real zero peak, while a day without rows was never measured — it is excluded from `points` and visible as `coveredDays < totalDays`, never drawn as a zero. The web overview charts only the real peak points (the old mapping presented daily active users under the peak-online label) and renders the timezone/granularity/coverage line under the spark. Boundary: no business-timezone config exists yet, so the day boundary is UTC by declaration; intraday partial coverage of boundary days is not tracked.
- Facade query parameter semantics (DATA-029): `/analytics/facade/query` declares, per domain, the parameters it actually consumes (`facadeDomainSpecs` in `internal/api/analytics/facade.go`); unsupported input gets a field-level diagnostic (422 with `details` keyed by the offending field) instead of being silently ignored. The metric vocabulary is the domain response's top-level keys, and `metrics` narrows the payload to that subset (absent/empty returns the canonical shape); filter keys outside the domain's declared set (`cohort` is retention-only, `days` is warehouse-only) are diagnosed; `timeRange` maps to `startDate`/`endDate` for date-range domains, to an hour lookback for invocations (capped at 30 days instead of silently snapping to the 24h default), and is rejected for fixed-window domains (realtime resolves its own 15-minute liveness window; warehouse resolves its window from `filter.days`). Web and mobile client tests cover different windows producing different requests/results. Boundary: cross-domain metric-caliber unification (windows, dimensions, denominators, source freshness) remains DATA-006.
- Per-domain summary time budgets (DATA-030): `/analytics/facade/summary` bounds every domain's wait under a per-domain budget (`facadeDomainBudget`, 5s, derived from the caller's context): a domain blocking past its budget reports the recognizable `timeout` card status with the budget error while the other domains still return in time; caller cancellation releases every pending domain wait immediately (abandoned domains report unavailable with a caller-context error, never dropped silently); and in-flight domain summaries are capped by a worker pool (`facadeSummaryConcurrency`, 4). The mobile dashboard renders the timeout chip and the error text explicitly.
- Inbound-chain acceptance (DATA-031): `scripts/e2e/analytics.sh` publishes fixed samples through the real `cmd/ingest` entry with test HMAC credentials — accepted batch, duplicate re-submit, invalid batch (DATA-016: 400 + `details.index`, nothing enqueued), header/`game_id` mismatch, fractional `amount_cents` rejection (DATA-018) and nonce replay (429) — and verifies the downstream ClickHouse shapes: raw rows collapse onto the derived event-id natural keys, the payment amount survives the chain intact, `minute_online` covers distinct fully-elapsed minutes, and `daily_revenue` aggregates the exact cents. The direct-Redis XADD worker test is retained to isolate worker behavior from ingest.
- Session-length distribution (DATA-037): `/analytics/warehouse/sessions` returns the length distribution of **ended** sessions from the ClickHouse pipeline A only (the bridge `session_end`/`session.end` events; the relational BehaviorEvent table is a separate pipeline and does not feed this endpoint). Input contract: an end event counts only when it carries both a non-empty `session_id` and a numeric `duration_ms` prop (`JSONHas` pre-filter; string/NaN/Inf/negative values land in `invalidDurations`, never in the distribution). Policy: the latest end event per session wins (redelivered or repeated closes collapse onto one session), durations are **never imputed** — a started session with no valid end inside the window is disclosed as `unresolved` instead of assuming a length, and duplicate heartbeat-driven starts do not inflate anything. Sessions are attributed by their end time, so a session that started the previous day but ends inside the window counts exactly once. The response materialises 11 fixed half-open buckets (`0-30s` … `12-24h`, `24h+`), cause counts sorted by volume, and nearest-rank `avg`/`p50`/`p95` (milliseconds); the raw scan is bounded (`maxWarehouseSessionRows`, 50000) and hitting the cap marks the response `sampled` instead of presenting a truncated read as complete. The e2e script plants one underscore-spelling and one dotted-spelling (cross-day) end sample and proves the endpoint's predicate family (`event IN (...)` + `JSONHas`) runs on the real engine. Boundary: heartbeats never extend a session's duration; sessions still open at query time remain unresolved; source unification across pipelines stays with DATA-002.
- Publisher factory fail-fast (DATA-043): `mq.NewFromEnv` refuses construction when `REDIS_URL` is unparseable (`mq.NewRedis` returns an initialization error instead of silently selecting the noop publisher), and the ingest entry exits non-zero before opening its listener — a misconfigured address can no longer acknowledge publishes while dropping every event. Empty-write mode is reachable only through explicit `ANALYTICS_MQ_TYPE=noop`.
- Result-stream iteration errors are honored (DATA-044): every warehouse reader that walks ClickHouse rows (DAU, online, revenue, session-length distribution) and the pipeline monitor's scope query check the driver `Err()` after iteration — a stream that dies before the first row or mid-read surfaces as a warehouse query failure (HTTP 500 via the warehouse error mapping) instead of a truncated point list presented as a successful payload; full reads and empty reads keep their normal shapes.
- Listener failures terminate the ingest process (DATA-045): an occupied port at startup or a mid-run listener death surfaces as the process exit error (non-zero exit via the CLI error path) instead of being logged while the process keeps running without serving; SIGTERM on a usable port keeps the graceful shutdown.
- Event and payment batches flush independently (DATA-050): the worker's single flush path (periodic and final) attempts both streams and reports their failures separately (`errors.Join`) — an event Send failure no longer strands payments. While event sends keep failing, payments still land in ClickHouse, their deferred refs still ACK, revenue aggregation commits and the checkpoint advances; the failed event batch is dropped with its messages left pending for the reclaim path (ARCH-011 semantics per stream). Boundaries: a permanent event failure still leaves event rows unwritten and their messages cycling through reclaim (surfaced by the DATA-047 pending-ack readings); per-stream error surfaced is the joined error, callers that log one line see both causes.
- Stable dedup identity across redelivery and requeue (DATA-051): the worker-derived event id for events without a producer `event_id` is a UUIDv5 over an identity-only fingerprint (game/env/raw ts/event/user/session/client id/canonical props) — retry bookkeeping is deliberately excluded. The requeue path rewrites the wire payload (`retry_count` folded back in, JSON re-marshaled with sorted keys), yet every redelivery form converges on the same event id: raw redelivery of the original bytes (Send succeeded but ACK failed, or PEL reclaim after a restart) and requeue copies whose bytes differ from the original. Verified by driving the real requeue branch — a forced append failure makes `processMessage` requeue the message, and the test reads the mutated bytes back from the stream and re-processes them (`internal/analytics/worker/data051_stable_dedup_across_requeue_test.go`). Boundaries: producer-supplied valid UUIDs pass through untouched; different logical events still derive different ids (folding is not conflation); payment dedup remains `order_id` read semantics (DATA-004/056).
- Idempotent requeue and dead-letter transfers (DATA-052): moving a message to the retry copy or the dead-letter stream is one atomic Lua script — XADD the target, SET a done marker, XACK the source message — so the target write and the source ACK cannot split. A script runtime error aborts before the XACK, so the message stays pending and reclaim retries cleanly; a re-run after an unknown client timeout or by a concurrent worker sees the marker and reduces to the ACK alone, never duplicating the retry copy or the dead letter (previously an XADD-success/XACK-failure split could dead-letter the same source message twice and give a retried message duplicate retry copies). The marker TTL (24h) only bounds key growth — by the time it exists the source message is already ACKed by the same script. Boundaries: the final XACK runs under pcall (a missing consumer group has no PEL, so there is nothing left to lose); a permanently failing target write leaves the source message cycling through reclaim (surfaced by the DATA-047 readings).
- Failed flush retries held rows instead of dropping them (DATA-053): a periodic batch Send that fails now holds the failed rows in memory together with their wire payloads instead of dropping the batch and its deferred ACK refs — the next flush round re-derives the rows from the payloads and retries the Send, so a short warehouse outage recovers without a reclaim round-trip and every failure is observable (a WARN per failed round with the attempt count) instead of silently cycling messages pending with a zero retry count. A record whose flush has failed maxPendingRetries (3) rounds is isolated through the idempotent dead-letter transfer (DATA-052), which ACKs the source so reclaim stops cycling it; a held payload that no longer decodes dead-letters immediately (retry_decode_failed) as a permanent bad record; and a message that leaves the pipeline through the requeue/dead-letter path drops its held copy, so the stream retry copy supersedes it instead of writing the record twice. Payment revenue deltas commit exactly once per source message even when a reclaim race puts two refs for the same message in one Send. Boundaries: held rows live in memory — a crash before a successful Send loses nothing because the messages stay PENDING and reclaim redelivers them after restart; the supersede check is per source message id, so a held row and a redelivered fresh row of the same message never both land.
- Single event-time contract for raw rows and aggregation (DATA-054): the detail insert (`normalizeTimestamp`) and the aggregate touch (`touchAgg`) now derive the instant from one shared parser (`parseEventTime`) that accepts RFC3339 with any offset (business-timezone producers, normalized to UTC), the ClickHouse datetime layout, and unix epoch seconds/milliseconds. Previously the aggregation side parsed RFC3339 only and fell back to `time.Now()`, so an epoch-ts or old event landed a correct historical raw row while its DAU/online buckets were thrown at the processing-time day/minute — a bucket that drifted on every replay. Explicit invalid disposition: empty or unparsable `ts` reaches neither path — the raw insert passes the value through (ClickHouse Append errors, the message retries into the dead letter) and the aggregation skips the event, so no bucket member can exist without an underlying raw row (rebuild-from-raw invariant intact). Boundary: the ClickHouse Go driver parses appended DateTime strings in the client location — the production worker runs in a TZ=UTC container, so stored wall clocks are UTC; on a developer box with a local timezone the DATA-054 drill pins the process to UTC to mirror the production posture.
- Week/month paying users are deduped over the actual window (DATA-056): `paymentsSummary` no longer sums per-day `COUNT(DISTINCT user_id)` values for `groupBy=week|month` — a player paying on two days of one ISO week/month was counted twice. Scope-matched `PaymentsModel.PayerDays` supplies distinct day/user pairs, and `summarizePaymentsWithPayerDays` dedups identities per bucket key (`YYYY-Www` / `YYYY-MM`) while Revenue and Transactions stay additive from daily rows. Pairs whose day has no matching revenue bucket are skipped, so no phantom bucket or payer is introduced; day grouping keeps its original semantics. Boundary: payer identity is `user_id` per the existing distinct-user contract; a user paying under different ids remains two payers.
- Consumer-group-scoped checkpoints (DATA-055): the persisted checkpoint key includes the consumer group (`<prefix>:<group>:<stream>`), so two groups sharing one stream keep independent high-water marks instead of overwriting each other's with an older progress value (previously a slower group's late persist rewound the shared key, and a restart resumed a faster group from the slower position). Migration rule: the legacy no-group key (`<prefix>:<stream>`) is read once as the adoptCheckpoint monotonic floor and never written again — group creation and WORKER_GROUP_RESET read the group-scoped key exclusively, so a second group added after an upgrade cannot inherit another group's progress and silently skip its own backlog; a fresh group starts at its declared position. Boundary: a group recreated after a pre-upgrade Redis loss falls back to its declared start position — the replay is absorbed by the ClickHouse natural-key dedup contract (event_id / order_id).
- Invocation latency with a published methodology and bounded resources (DATA-049): `/analytics/invocations/summary` publishes its latency contract in a `latency` object — the p95 rank is integer nearest-rank (`ceil(0.95*n)`, 1-based) over recorded durations, so small samples keep their full rank (the previous float `int(n*0.95)-1` reported the minimum as p95 for two samples); rows without a recorded `duration_ms` are counted as `missingDuration` and never imputed; and the scan is capped at 50000 newest rows (`timestamp DESC, id DESC` as the deterministic tiebreak) so memory and query time stay flat under high load — a capped read is disclosed as `sampled` with its `coverage`, and avg/p95 always describe exactly the scanned subset. The trend endpoint scans at most 10000 newest rows too (the old oldest-first order silently froze the chart on a stale prefix under load) and returns a `sample` object (`totalEvents`/`scannedEvents`/`sampled`/`coverage`). Boundaries: when the cap is hit the summary describes the newest slice, not the whole window; the facade passes the same summary struct through, disclosure included; `hours` outside 1..720 still falls back to the 24h default.
- Publisher retains the source stream by consumer progress (DATA-048): the Redis publisher no longer passes `MaxLen` on XADD — a blind head trim that evicts entries a consumer group has not even delivered. Publishing adds first and, only once the stream is above the `ANALYTICS_REDIS_MAXLEN` cap, trims with `XTRIM MINID` to the safe boundary: the oldest entry any consumer group still needs (the oldest pending-ack entry, or strictly after last-delivered when nothing is pending), pinned on the slowest group, so only entries every group has both delivered and acknowledged are removed. A worker outage with backlog beyond the cap retains everything and recovery replays all undelivered and un-ACKed entries; `ANALYTICS_REDIS_MAXLEN_APPROX` now selects the approximate MINID trim strategy. Boundaries: while group progress cannot be read nothing is trimmed — retained may stay above the cap until the backlog drains (surfaced by the DATA-047 readings); the per-publish cost while above the cap is one XLEN plus the group/pending progress reads; the worker's retry re-queue (DATA-019) adds without trimming and the consumed prefix is cleaned on the next publisher publish; the dead-letter stream keeps its own fixed bounded cap.
- MQ backlog read from consumer-group progress (DATA-047): the ingest backlog sampler and the pipeline monitor report three separate readings — retained physical length (XLEN), undelivered lag and delivered-unacknowledged count from the worker group (`WORKER_GROUP`, default `analytics-worker`) — instead of presenting XLEN as backlog; a stream that has been fully consumed and ACKed falls back to zero backlog even though its physical length is unchanged. Readings the broker cannot provide are displayed as unknown (`null` in the ingest healthz `backlog` object and in alert details), never as fake zeros: the Kafka publisher no longer returns a fixed 0 (it reports nothing without an AdminClient), a Redis below 7 that omits the lag field reports undelivered unknown while pending-ack stays valid, a missing consumer group counts every retained entry as undelivered (the group is created from the stream start on first worker start, DATA-023), and only a complete healthy progress reading may resolve an `mq_backlog` alert (DATA-022). Boundaries: the legacy `events_pending`/`payments_pending` healthz fields now mean undelivered+pending-ack (null when unknown), not XLEN; the trimming policy (what may be dropped) remains DATA-048; Kafka has no backlog reading at all.
- Request body cap applied before auth reads (DATA-046): the ingest endpoints enforce the same actual byte limit (`ANALYTICS_INGEST_MAX_BODY_MB`) at the auth layer before any byte is read — a request whose declared length exceeds the cap is rejected without reading the body, and a chunked upload without `Content-Length` stops at the cap via `http.MaxBytesReader`; oversized requests get a stable `413 body_too_large` before signature verification instead of being fully buffered for the digest. Auth verification and business decoding consume the same bounded bytes; the handler-level oversized detection matches the cap by error type (`http.MaxBytesError`) rather than message text. Boundaries: a body of exactly the limit passes; the metrics middleware declared-length pre-check stays as a secondary branch; a configured limit of 0 rejects every body at the gate.
- Boundary: the payments table has no dedup column; identical payment re-submission still appends a second raw row and relies on `order_id`-keyed read semantics for reconciliation (tracked by DATA-004/051/056).

## Metric groups

- **Foundation:** DAU, WAU, MAU, stickiness, and D1/D7/D30 retention.
- **Progression and economy:** level completion, conversion, source sinks and sources, balance signals.
- **Engagement and social:** session length, feature use, team and guild activity, messaging.
- **Combat and content:** win-rate distribution, character balance, ranked distribution, PVP/PVE participation.
- **Campaign and operations:** participation, completion, incremental revenue, push delivery and conversion.
- **Experience:** page dwell time, interaction and error rates, discovery, latency, and network quality.

## Operational shape

1. Start Redis and ClickHouse.
2. Run `ingest` with the configured HMAC secret.
3. Run `analytics-worker`.
4. Run the Server and open the Analytics console.

Schema and pipeline changes should be additive where practical. Existing events must remain queryable while new dimensions or aggregates are introduced.
