## 2. sidecar-agent (game server)

| Dimension                    | Content                                                                                                                                                                                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One-liner                    | The GM infrastructure proxy beside the game server (**external side**), **business-related functions only**: function registration and invocation (Function Registry) + process supervision (Supervision) + self-probes + host/scheduled-task reporting |
| Deployment (runs beside)     | **On the game server host/same segment (external side)** (sidecar shape, deployed with the game server); connects upstream to the croupier server to register                                                                                           |
| Monitors                     | Same-host game processes (`managedProcesses`, S1/S2 snapshot/launch/circuit-breaking), local resources (gopsutil collection), this instance's registered functions, host info and scheduled tasks (health report scope)                                 |
| Inputs                       | From the server: function invocations, process operations (start/stop/restart), config sync (configsync), rules/allowlists                                                                                                                              |
| Outputs                      | Registration/heartbeat/metric piggyback (MetricsReport), supervisor snapshots and events, execution audit (execlog), host and scheduled-task health info                                                                                                |
| **Prohibited**               | **No bastion-style remote access** (SSH/RDP/VNC into intranet machines is devops-agent's exclusive domain); the sidecar only reads + supervises its own game processes — no interactive terminals, no file-transfer proxy                               |
| Boundaries with other agents | No remote access/bastion (devops only), **never reads business database change logs** (capture only), no third-party ingest/external probing (roadmap placeholders only)                                                                                |
| Health probes                | Liveness (game process alive, same source as supervisor sampling) + Heartbeat                                                                                                                                                                           |
| Execution audit              | Every function invocation/process operation/config hot-update writes execlog (operator = GM account or system)                                                                                                                                          |
| Scope ownership              | Registration carries `game_id`+`env`; process/function/audit data all filtered by scope                                                                                                                                                                 |

## 5. Shared Modules (all four agents consume; no one writes their own)

### 5.1 healthprobe (health probes, first deliverable)

Three semantics mirroring k8s probe terms (finalized in agent-core §6.1): **Liveness** / **Readiness** / **Heartbeat** (periodic). The four agents' consumption mapping (synthetics behavior as of 2026-10-20, not yet a healthprobe consumer):

| Agent            | Liveness                                | Readiness                                                                                                     | Heartbeat        |
| ---------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------- |
| sidecar-agent    | Game process alive                      | Server upstream link reachable                                                                                | Generic stamping |
| devops-agent     | Self alive                              | Allowlisted host ports reachable / guacd channel usable                                                       | Generic stamping |
| capture-agent    | Self alive                              | Database reachable / replication stream healthy                                                               | Generic stamping |
| synthetics-agent | Self alive (core/supervisable contract) | Probe targets reachable (native HTTP and go-plugin plugins carry it separately; not yet wired to healthprobe) | Generic stamping |

Probe results go straight to the console: each page's instance list carries status lights + liveness/readiness verdicts + heartbeat age (last heartbeat age).

**Modeled by system role (failure windows, user order 2026-10-09)**: probes do not only check current liveness — every monitored system (target) records its failure window (start/recovery/duration), queryable historically, with probe data carrying a timeline; troubleshooting answers "in which time window was the service unavailable" directly. Model and retention in agent-core §6.1; console display in [the Agent panel design](agent-dashboard-design.md) §2.

**The probe system's three layers and unified assembly (review-finalized 2026-10-14; authority: the health review)**: kernel = this package (one implementation); protocol probes = http/tcp/process/db + the game protocol skeleton; execution location is by perspective (every agent can configure `probe.targets`; devops is the primary user — decided by the user on 2026-10-14). **Implementation layer ≠ instance layer**: sharing core code ≠ a single point of origin. The upstream asymmetry policy (aggregates for normal, details for anomalies) and the sampling strategy (server-delivered, default 30s) are in the same brief §13. Current status (2026-10-20): capture probes database reachability (TCP layer); devops has zero probes pending M1; synthetics-agent liveness goes through core/supervisable, with target reachability carried by the kernel's protocol probes and go-plugin plugins — not yet a healthprobe consumer.

### 5.2 execlog (unified execution audit)

**Every agent's every execution leaves an audit record** (user order, 2026-10-09). Fields/the audit-first admission gate/retention and export config points in agent-core §6.2. Console side: each agent page's "execution records" list + filters (operator/result/time range) + detail drill-down (inputs/full results), all scope-filtered.

### 5.3 herald (alert delivery outlet)

Capture alerts / healthprobe failure windows / devops anomalies (unreachable allowlisted hosts, audit refusals, etc.) are delivered via **herald** (the notification orchestration and delivery platform) — croupier integrates as a client (courier-style); **channels/recipients are configured on the herald side**, and croupier only reports events without configuring recipients; the alert page remains the truth, and herald being unreachable never blocks the alert chain. Integration details in the herald integration brief. **M2 landed (2026-10-10)**: the `internal/platform/outlet` outlet adapter + the `herald:` config section (off by default), with the supervisor circuit breaker as the first event source; implementation-vs-brief differences in the brief's §8.

## 7. Scope Ownership Rules (game_id + env, mandatory)

The authoritative contract is [game environment scope §14.7](../architecture/game-environment-scope.md); page rules are [the four-console design](agent-dashboard-design.md) §5.

1. **Explicit identity**: all four roles' configs and registrations require non-empty `gameId/env`, with proto/DB using `game_id/env`; they are fixed identity fields — never only user labels or hostname-derived; missing means startup/registration failure.
2. **One instance, one ownership**: each agent binds exactly one game environment; multiple independent instances and directories deploy per scope on the same host; plugins, targets, hosts, capture sources, tasks, configs, statistics, audit, and logs all inherit the same scope — cross-scope assignment is forbidden.
3. **Explicit labeling**: the four pages' titles, instance rows, details, and operation confirmations always show gameId/env, reusing the global selector; switching cleans up old requests, caches, drawers, and pending operations, and late responses never leak across pages.
4. **Server-side isolation**: list/aggregate/detail/control/download/replay and local/cluster/fallback paths all validate ResolvedScope, following the convention that scope requests come only from context/headers.
5. **Offline history**: displayed per the persisted last-known scope with data time and staleness marked; live control forbidden; old records without ownership stay out of the four pages, keep authorized diagnostic logs, and never get cross-scope fallbacks.
