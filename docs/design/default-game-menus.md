# 游戏运营默认菜单与建议业务能力

2026-10-17 用户确定玩家工作台、邮件与补偿、封禁管理、订单核查、活动配置作为默认菜单分类及建议实现；结合现有公告、审计分类，默认提供七个顶级分类。菜单模板已调整，表中业务子页仍需游戏能力接入、页面发布与挂载，不代表已实现。

## 1. 默认分类与建议页面

| 排序 | 分类       | 稳定 menuKey   | 建议挂载页面                                          | 业务闭环要求                                                         |
| ---- | ---------- | -------------- | ----------------------------------------------------- | -------------------------------------------------------------------- |
| 10   | 玩家工作台 | `player`       | 玩家/角色查询、玩家详情、资产视图、登录历史、操作历史 | 明确账号/角色/区服身份、游戏数据来源及更新时间，资产写操作走游戏能力 |
| 20   | 邮件与补偿 | `mail`         | 邮件任务、补偿任务、投递/领取记录、失败处理           | 对象快照、预演人数及总额、审批、逐对象执行凭据、幂等及失败重试       |
| 30   | 封禁管理   | `ban`          | 封禁名单、封禁/解封申请、处置历史                     | 对象/区服、原因、期限、审批、游戏执行结果及到期处理                  |
| 40   | 订单核查   | `payment`      | 订单查询、到账核查、补单申请、对账差异                | 支付凭据与游戏到账凭据分别记录，补单幂等、审批及执行后复核           |
| 50   | 活动配置   | `operation`    | 活动列表、配置版本、发布计划、生效与回滚记录          | 配置校验、目标范围、游戏时区、生效时间、发布审批及回滚限制           |
| 60   | 公告管理   | `announcement` | 公告列表、发布计划、投放记录                          | 语言/渠道/区服范围、定时生效与撤回、实际投放结果                     |
| 70   | 操作记录   | `audit`        | 执行记录、审批记录、批量任务结果、变更历史            | 按操作者/目标/时间/结果追踪，串联 operationId、审批及游戏侧凭据      |

前五类是优先接入的游戏运营工作流，后两类保留既有常用入口；推荐先完成单玩家查询与一条补偿操作的端到端链，再扩批量运营。

建议子页不是默认创建的空菜单节点，避免导航层级过深或出现大量无数据入口；实际页面可以按游戏组合，优先使用“分类 → 已发布页面 → 页面内 Tab”两级导航。

## 2. 默认初始化与定制规则

- 单一模板为 `configs/default-menus.json`，server 从 `bootstrapData.baseDir` 读取；沿用 `MenuSeeder` 按 `(gameId, env)` 的首次菜单读取惰性创建，不因新增游戏记录就预建所有环境数据。
- 新 scope 首次访问菜单管理或运行控制台时自动创建七个顶级分类，labels 使用 zh-CN/en-US，图标来自现有允许列表。
- 保留既有 `player/operation/payment/announcement/audit` key，新增 `mail/ban`，已存在分类的标题、排序、可见性、权限与页面挂载均不覆盖；旧 `operation` 是稳定 key，不要求已有用户将“运营”重命名为“活动配置”。
- 已有 scope 沿用一次补缺及持久标记语义：未处理的旧 scope 仅补缺失 key，已有补缺标记的 scope 不因升级模板自动补新分类；管理员按本文手工创建 mail/ban 即可，不通过删除标记强制升级。
- 用户可以改名、调整排序、隐藏、增加子分类或删除分类；部分删除后不会因重启复活；全部删空且重启后会按空 scope 规则重建，彻底关闭默认分类可移除种子文件或配置为空数组。
- 分类与页面挂载严格属于当前 gameId/env，不能在环境之间共享同一菜单行；跨 scope 复制配置须显式创建目标 scope 的新菜单及页面挂载。

## 3. 分类、页面与能力的关系

```text
默认菜单模板 → 当前游戏环境菜单分类
游戏 SDK / 外部函数适配插件 → 函数契约
函数契约 + 页面设计 → PageSpec 发布 → 挂载菜单 → 可使用的业务页面
```

默认初始化只创建分类，不安装业务扩展、不创建业务表、不注册伪函数、不自动批准页面、不发放任何操作权限。空分类沿用控制台的空分类页面及页面挂载引导；只有已发布且已挂载的页面才进入对应分类，不显示模拟数据或无执行链的操作按钮。

业务页面可由官方扩展、游戏 SDK 函数或外部函数适配插件承载，统一复用授权、审批、任务、审计及发布快照；菜单可见性不替代后端权限。第三方支付凭据、游戏资产和角色状态的权威归属由实际接入方声明，不能因默认分类存在就把 Croupier 本地副本当作游戏真值。

## 4. 平台固定菜单的关系

本模板用于动态运行控制台的游戏业务导航。Agent 四类页面、监控告警、资源/函数目录、页面工作台、菜单管理、用户权限和系统设置继续使用现有平台导航；它们不在每个游戏环境重复创建为业务分类。

客服工单、数据分析、区服管理等可以按实际游戏需要后续添加或挂载现有能力，不继续扩大首版默认空分类。

## 5. 验证与边界

- 配置必须可由真实 `LoadSeedMenus` 解析，七个 key 唯一、排序递增、标签符合 BCP47、图标可渲染。
- 沿用 seeder 的 scope 独立、重复访问幂等、已有分类不覆盖及用户删除不复活回归用例。
- 不变更 PageSpec wire、发布和菜单挂载契约，不涉及线上数据迁移；已运行服务需使用更新后的 bootstrap 文件并重启后加载模板。
- 本次默认分类交付不等于业务子页完成，五类业务闭环单独列入 todo，按真实游戏接入验收。
