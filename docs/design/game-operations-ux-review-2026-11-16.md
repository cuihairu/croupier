# 游戏运营后台体验审查与改进方向

状态：设计建议与待办，**不代表已经实现或验收**。审查时间：2026-11-16。

## 范围与结论

走查了已部署后台的登录、首页、运行控制台、函数/资源目录、页面工作台、审批中心、节点维护，以及玩家管理演示模板和详情。两个查看过的游戏 DEV 环境均未显示已发布页面；玩家管理是预览模板。没有执行充值、封禁、邮件或发布，也没有验证真实游戏权限与写入链路。线上部署版本与本地源码须单独核对，不能直接假定线上对应当前提交。

界面主要围绕函数、契约和页面装配来组织。运营用户需要的玩家、订单、活动、待办和风险上下文没有成为主轴。控件有通用封装，但相同业务字段在列表、详情和操作流程中的语义未统一；专业感的缺口由信息架构、交互模式、数据表达和视觉层级共同造成。

## 已观察到的问题

| 页面/组件    | 观察                                                                            | 用户影响                                     |
| ------------ | ------------------------------------------------------------------------------- | -------------------------------------------- |
| 首页         | 多处重复解释能力供给、页面装配、发布验证，并出现产品建设进展                    | 常用任务和真实待办难以快速识别               |
| 主导航       | 函数、SDK、页面构建与玩家、客服、风控、运维并列                                 | 不同角色面对同一庞大功能树，工作上下文不清   |
| 函数目录     | 大面积说明卡和提示框先于列表                                                    | 首屏工作区被说明挤占，重复阅读成本高         |
| 控制台空态   | 每个菜单各显示一张无页面卡片，展示内部 key                                      | 空态占空间，缺少面向当前角色的下一步         |
| 玩家模板列表 | 七个筛选条件默认全部展开；每行同时显示查看、封禁、充值、邮件、编辑、删除        | 高频搜索不突出；重复主按钮与操作列挤占数据列 |
| 玩家模板详情 | 列表显示中文状态和格式化时间，详情显示 `active` 与原始 ISO 时间；余额仅显示数值 | 同一实体的含义和时区不一致，难以建立信任     |
| 登录/演示    | 登录占位符仍含模板名称，演示游戏名称偏测试术语                                  | 首次使用呈现未完成感                         |

视觉上，页头、说明、提示、统计与列表普遍采用相近卡片、阴影和标签，争夺同一级注意力。节点维护等高密度页面需要明确数据、状态和动作的优先级。

## 产品与导航

按工作任务组织入口，同时保留现有权限与功能：

1. **运营工作台**：玩家查询、订单、邮件补偿、活动、审批、执行记录和待办。
2. **开发与接入**：函数与资源契约、OpenAPI、页面构建、调试和发布。
3. **平台管理与运维**：游戏/环境、账号权限、节点、配置与治理。

角色和权限决定可见内容；管理员仍可访问完整能力。当前游戏、环境保持可见，区服、渠道与时区在业务需要时提供；提交高影响操作时重新展示实际作用域。首页优先呈现可用的待办、异常、最近处理与常用入口；数据尚未接入时明确状态，不生成虚假指标。

## 组件边界

| 层       | 职责与示例                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------- |
| 基础控件 | 复用 Ant Design 的按钮、输入、表格、抽屉、弹窗及无障碍能力                                        |
| 业务语义 | 玩家身份、游戏/区服、货币金额、道具数量、业务状态、带时区时间；统一空值、格式、本地化与可复制规则 |
| 交互模式 | 查询工具栏、资源列表、对象详情、操作面板、变更预览、执行回执；统一加载、空、错误、权限与部分结果  |
| 场景页面 | 玩家查单、邮件补偿、封禁、订单审核、活动发布；根据实际契约配置可用操作                            |

现有 `ResourcePageRenderer` 继续承担装配，逐步把列表、详情和操作流程提取为可组合模式；表单继续消费现有 Schema/语义元数据。不要让字段类型单独决定业务重要性，也不要让模板默认提供游戏未支持的创建、删除或资产操作。列表、详情、确认与回执复用同一语义映射；缺失单位、时区、权限或能力时显式标注未知，不伪造。

## 标杆流程

先贯通**玩家查询 → 玩家详情 → 邮件补偿 → 目标与内容确认 → 执行回执**：

- 首屏以玩家 ID/昵称等高频检索为主，高级筛选按需展开；查询保持游戏和环境作用域。
- 详情以玩家身份为锚，按实际数据能力展示角色、资产、订单、邮件和操作历史；列表与详情状态、时间、单位一致。
- 补偿流程展示目标、作用域、内容、数量、理由和实际可用权限；提交前提供可核对的摘要。
- 结果只展示真实支持的状态和回执，区分提交、执行、失败及部分成功；记录可追溯标识。审批、幂等、重试或回滚必须以现有服务契约和证据为准。
- 无真实游戏接入时可用可控 fixture 验证交互，不将 fixture 视为真实游戏验收。真实发布与接入仍沿 `UI-001` 等既有任务追踪。

## 视觉与验收

以操作型界面的可扫描性为准：一页有明确标题、作用域、首要任务和次要动作；常规信息用安静的表面与边界，强调色用于选中、主要动作和语义状态。统一表格行高、列宽、数字/时间对齐、筛选间距、抽屉尺寸及控件状态。危险操作的视觉样式与权限/实际能力对齐，不以颜色作为唯一提示。

验收至少覆盖 1440px 和常用笔记本宽度、键盘操作、中英文、长字段、空/加载/错误/部分成功、游戏环境切换与旧结果失效；通过截图和真实交互检查，而非仅凭组件单测。技术术语放在需要它的管理上下文或按需帮助中。
