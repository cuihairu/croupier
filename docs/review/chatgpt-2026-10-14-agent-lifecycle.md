- **性质**：**外部建议，不是本仓事实陈述**。原文亦自述：「**Reconciler 是建议新增的架构组件，并不代表当前 Croupier 已经实现了完整的期望状态协调机制**」——执行前必须对代码核验（file:line）。
- **承接**：[probe-architecture](chatgpt-2026-10-14-probe-architecture.md)（三层结构）、[probe-adapter](chatgpt-2026-10-14-probe-adapter.md)（外部适配器契约）。本份把前两份提到的**受管对象**统一成一个模型。

## 一、整体架构：期望状态协调（Reconciler）

Server 声明程序**期望**处于什么状态 → Agent 检查**本地实际**状态 → 逐步执行启动、停止、更新、配置发布。

调用链：`Server → Desired → Task → Agent → Reconciler → {Scheduler, Supervisor, Updater, Config, Health} → Supervisor → Runtime → {Probe, GameTool}`

`Reconciler` 为**建议新增**组件，本仓当前未实现。

## 二、Agent 应管理哪些生命周期

| 能力                     | 归属           | 说明                               |
| ------------------------ | -------------- | ---------------------------------- |
| 安装、启动、停止、重启   | 是             | 统一进程管理                       |
| 开机自启与异常退出恢复   | 是             | **区分程序崩溃与主动停止**         |
| 定时启动、停止、重启     | 是             | 使用统一调度器                     |
| 更新二进制文件           | 是             | 下载、校验、切换、回滚             |
| 更新配置文件             | 是             | 版本化、校验、原子发布             |
| **修改探测频率**         | 是             | 作为受管程序的**期望配置**         |
| 暂停与恢复               | 是             | **明确暂停的是调度、程序还是探测** |
| 健康探测                 | 是             | **复用 `core/healthprobe`**        |
| 异常恢复策略             | 是             | 重启、退避、熔断、人工介入         |
| 查看日志、版本、运行状态 | 是             | 统一上报 Server                    |
| **任意远程 Shell 执行**  | **不默认开放** | 独立授权、白名单、审计             |

**关键边界**：更新二进制和配置 **≠** 允许任意远程命令执行。程序操作应建模为**明确、受授权的动作**，而不是开放一个通用命令执行入口。

## 三、统一的受管程序模型 `ManagedProgram`

它可以同时表示**游戏辅助程序**与前两份评审里的**外部探测适配器**——把两类受管对象合并为一个模型。

结构示意：`Schedule ScheduleSpec` / `Recovery RecoverySpec` / `type ProgramDesiredState string ...`

## 四、四个必须分清的状态

**运行状态 / 管理状态 / 调度状态 / 更新状态** —— 混为一谈会导致「更新中」被当成「已停止」之类的误判。

## 五、更新二进制怎么做

- 二进制通过**可信来源分发**，校验**内容哈希与签名**。
- **不能只原子替换一个二进制就宣称更新安全**：还要考虑进程正在运行/文件占用、数据库或配置兼容性、**新版本启动失败后的恢复**。
- **Agent 自身升级应单独设计**，不能简单依赖普通受管程序更新逻辑。

## 六、定时任务与健康恢复如何协作

建议**统一调度模型，但不要把定时任务与健康恢复混成同一个执行逻辑**。

## 七、对本仓现有架构的影响（原文自述）

原文明确这是**建议新增**，并提示会牵动 Scheduler / Supervisor / Updater / Config / Health 诸面。

## 核验与采纳判定（本仓 2026-10-14）

| 主张                          | 判定               | 说明                                                                                                                                  |
| ----------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| 引入 `Reconciler`             | **待定，倾向采纳** | 本仓现无完整期望状态协调；须先核现有 `Supervisor` 与 dispatch 的职责边界，避免与既有机制重复                                          |
| `ManagedProgram` 统一受管对象 | **采纳**           | 直接解决「游戏辅助程序」与「外部探测适配器」两套模型的分裂；与 probe-adapter 的 `ProbeAdapter` 清单**关系必须说清，不许三套配置并存** |
| 「修改探测频率」属期望配置    | **采纳**           | 与用户 2026-10-14「服务器控制采样频率/时段/特殊时间点，不设则默认」**完全吻合**，是同一诉求的上位模型                                 |
| 区分程序崩溃与主动停止        | **采纳**           | 否则主动停机也会触发恢复，造成误启                                                                                                    |
| 暂停要指明暂停对象            | **采纳**           | 暂停调度 ≠ 暂停程序 ≠ 暂停探测                                                                                                        |
| 更新不等于远程 Shell          | **采纳为硬边界**   | 与本仓权限收敛方向一致；开放通用命令执行入口是安全反模式                                                                              |
| 不能只原子替换二进制          | **采纳**           | 必须覆盖运行中进程、文件占用、数据/配置兼容、新版本启动失败回滚                                                                       |
| Agent 自身升级单独设计        | **采纳**           | 自升级失败会让 Agent 失联，与普通程序更新的风险面不同                                                                                 |
| 定时任务与恢复分开实现        | **采纳**           | 统一调度模型，但执行逻辑不合并                                                                                                        |
