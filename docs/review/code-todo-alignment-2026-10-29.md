## 对“核心足够稳定吗”的判断

当前是**较完整的平台底座 + 未闭环的高风险运营执行保障**。注册、会话、路由、scope、发布快照、控制台与基本审批/任务/审计机制已有实际实现；没有必要因为这些缺口另拆微服务或重写 SDK。只读接入和受控集成可以继续推进，但必须按实际配置另行验收，不能由本审核自动批准上线。

真实补偿、发奖、订单补发与自动运营目前存在以下阻断因素：

1. 多入口治理不一致：同一函数经普通/页面调用会走政策审批，经任务/调度却未执行同等规则。
2. 策略故障可能被当作“没有政策”而继续执行。
3. 调度唯一记录在副作用之后写入，无法阻止双实例重复派发。
4. 执行可能没有成功持久化任务主记录；终态事件仍有丢失、重复 Start 仍无持久约束。
5. 游戏权威身份、持久去重/执行收据与未知结果核对尚未形成已验收的接入协议。UI 的幂等键、taskId 和成功 toast 都不能替代它。

以上属于正确性/治理缺口。性能、生产故障恢复和跨语言实际部署稳定性另有证据缺口，不能给百分比“成熟度”或保证 SLA。

## 已核实的新增关键发现

### R01 · P0 · task / schedule 没有完整执行治理

**VERIFIED — 源码装配。** `internal/api/task/service.go:75` 的 Start 已检查 scope、契约存在、禁用、分配与函数级 RBAC，这些能力应保留；之后在 `:142` 直接 runtime.StartTask。`internal/api/task/runtime.go:60` 直接调用 Dispatcher。该路径不执行 `EnforceFunctionPolicy`、审批创建和 `ValidateInvokeInput`。

`internal/api/schedule/service.go:Create/TriggerNow` 与 `internal/svc/scheduler.go:dispatcherAdapter` 同样直达 Dispatcher；调度中的 actor 字符串不等于每次触发重新授权。`internal/platform/functioninvoke/invoke.go:105` 起才包含政策/输入契约/审批的主要规则。模块级 JWT/scope 不等于函数级执行授权与审批。

影响：有合法基础调用权限但目标函数要求审批的调用者，可遇到不同入口处理不一致；已禁用/撤权/变更契约后的定时触发也没有统一的重新治理层。真实生产攻击/自动化账号矩阵 **NOT RUN**，本结论不声称已有事故。任务：**ARCH-024**，定义自动化主体、批准快照和所有入口的一致准入，复用已有治理服务。

### R02 · P0 · 政策存储故障被吞为“无政策、无错误”

**VERIFIED — 确定性诊断。** `internal/platform/functioninvoke/policy.go:78–85` 在 GetPolicy 报错时返回 `nil, nil`；Invoke 随后只有 functionPolicy 非空时才进入审批与相关审计分支。`internal/svc/service_context.go:403` 的 PolicyManager 初始化失败设 nil，也会跳过政策分支。

用缺失 function_policies 表模拟查询故障：原始 GetPolicy 返回错误，而 EnforceFunctionPolicy 返回 policy=nil、error=nil。诊断输出：

```text
lookup_error=true, enforced_policy_nil=true, enforced_error_nil=true
```

这是政策故障被掩盖的可复现分支，不表示测试了线上数据库。任务：**ARCH-025**；先明确 fail-closed/已批准 last-good 规则，不把默认 YAML 存在当成当前代码已安全回退。

### R03 · P0 · 定时任务先派发后抢唯一记录

**VERIFIED — 源码与确定性双 Manager 诊断。** `internal/tasks/scheduler/manager.go:145` 查 HasRunLog，`:207` 调 StartTask，`:216` 才 CreateRunLog，且返回值/错误都忽略。`internal/model/task_schedule_model.go:163` 的唯一索引只保证最终日志写一条，不能撤销已发出的第二次执行；server-local 报表路径也在执行后写日志。

使用同一 store 的两个真实 scheduler.Manager，派发处用屏障令两者都到达执行，再允许写唯一记录：

```text
same schedule+slot: dispatches=2, accepted_unique_logs=1
```

store/dispatcher 是确定性替身，模拟唯一键冲突；**没有把它宣称为真实多进程数据库 HA 演练**。代码时序本身已足以证明唯一索引放错阶段。任务：**ARCH-023**，领取在派发前，领取失败不执行；租约和崩溃恢复独立于游戏最终副作用去重。

### R04 · P1 · task_runs 写失败仍发送任务

**VERIFIED — 源码。** `internal/platform/dispatch/dispatcher.go:769` 用 `_ = writer.CreateRunWithMeta(...)` 忽略错误，再调用 Agent StartTask。前轮“先写 task_runs 再执行”的表述不完整：实际是先**尝试**写入，不要求成功。任务主记录缺失可能破坏查询/归属/取消与后续核对。真实 DB 故障注入 NOT RUN。任务：**ARCH-026**，写失败时执行计数必须为零；不能只解决 Agent 事件重放而保留此入口。

### R05 · P1 · descriptor 查询错误等同跳过校验

**VERIFIED — 源码。** `internal/platform/functioninvoke/invoke.go:285–298` 把 ListDescriptors 报错与确无 schema 合并为 return nil。它不能区分兼容旧函数与契约存储故障；高风险输入校验不应在查库失败时静默消失。故障复现 NOT RUN。任务：**ARCH-027**，先定义版本/快照与明确错误语义，再复用校验器收口。

### R06 · P1 · 批量总量仍接受失真整数/溢出

**VERIFIED — 执行当前 TypeScript 源码。** `web/src/components/PageRenderer/batchSelection.ts:summarizePerTargetTotal` 已修正空白字符串，但只检查输入 Finite/Integer，不检查安全整数和乘积。当前源码转译执行的结果：

```text
Number.MAX_VALUE × 2 → Infinity
Number.MAX_SAFE_INTEGER × 2 → 18014398509481982（不属于安全整数）
空串 × 2 → undefined（在途修复有效）
```

这并不证明默认模板的普通金额已经触发溢出；它说明通用确认 helper 缺少金额边界保证。任务：**REVIEW-005**，与业务金额单位/倍率/上限一并校验，避免 UI 展示可确认的失真总量。
