- **性质**：**外部建议，不是本仓事实陈述**。每条执行前必须对本仓代码核验（file:line）。
- **承接**：[chatgpt-2026-10-14-probe-architecture.md](chatgpt-2026-10-14-probe-architecture.md)（同日第一份评审，定三层结构与执行位置）。本份回答的是**上一份留下的关键问题**：私有协议多、每个游戏都要单独接，怎么扩展。

## 要解决的问题

游戏多为私有协议（通用的可能是 HTTP）。若每接一个游戏都要改 Croupier 核心，探测体系会被拖死。本份建议给出**外部适配器**方案：Croupier 不必成为所有游戏的协议专家，只提供稳定平台，让游戏开发者把协议能力接进来。

## 一、推荐的扩展模型

外部探测适配器由**游戏开发者实现**。只要遵守 Croupier 的外部调用协议，可用 Go / C++ / C# / Java 等任意合适语言实现私有协议探测。

## 二、为什么不用 Go 标准库 `plugin`

| 方案                    | 多语言     | 故障隔离     | 独立升级         | 主要问题                             |
| ----------------------- | ---------- | ------------ | ---------------- | ------------------------------------ |
| Go `plugin`             | 否         | 弱（同进程） | 受宿主约束       | 平台支持、Go 工具链与构建依赖约束多  |
| Go 接口编译进 Agent     | 否         | 弱（同进程） | 通常需重编 Agent | 适合内部模块，不适合外部生态         |
| **独立进程 + JSON-RPC** | 是         | **较好**     | 是               | 需定义 IPC、生命周期、权限控制       |
| 独立进程 + gRPC         | 是         | 较好         | 是               | 需管 protobuf 契约、依赖与端点       |
| WASM                    | 视宿主接口 | 沙箱较好     | 是               | 网络/原生 SDK/系统调用需额外宿主接口 |

> 原文注：「故障隔离」指进程崩溃不会拖垮 Agent 进程，**不等于完整安全隔离**。

## 三、外部探测程序怎样调用

采用**独立进程 + 版本化 IPC**（`croupier-probe-jsonl-v1`），而非把 Go `plugin` 作为唯一扩展机制。

**一个重要细节：不要为每次探测都启动一次进程** —— 进程启动成本会主导探测周期。需要常驻/复用机制（原文提及，未展开，须在设计中补齐）。

## 四、Croupier 默认提供的探测能力

内置**通用协议探测**与**有限的声明式探测**，让常见 HTTP/TCP 场景**不需要写代码**；复杂私有协议交给外部适配器。

## 五、外部适配器需附带描述文件

```yaml
apiVersion: croupier.io/probe/v1
kind: ProbeAdapter

metadata:
  id: com.example.game-a
  version: 1.0.0

spec:
  executable: ./game-a-probe
  protocol: croupier-probe-jsonl-v1
  capabilities:
    - login
    - handshake
  limits:
    maxConcurrency: 4
    defaultTimeoutMs: 5000
    maxTimeoutMs: 15000
```

- 清单**只声明**身份、入口、协议、能力。
- 游戏地址、环境、探测频率、**目标授权与凭证引用**由 Croupier 的探测任务配置管理，**不应硬编码进适配器清单**。
- **声明支持 `login` ≠ 已验证登录成功**：Server 仍需校验适配器版本、能力声明、授权范围，并以实际探测结果判定目标状态。
- 字段规范待正式实现前确定。

## 六、最重要边界：外部程序只探测，不控制平台

外部适配器**不应拥有 Agent 的全部权限**。原文给出能力归属表（外部只探测、平台控制权留在 Agent/Server）。

## 七、最终架构决策（原文收敛）

1. 保留现有公共探测内核，**不重复实现**状态机、失败阈值、故障窗口。
2. 新增**统一的外部探测适配器契约**：独立进程 + 版本化 IPC，**不把 Go `plugin` 当唯一扩展机制**。
3. 内置通用协议探测 + 有限声明式探测，HTTP/TCP 常见场景免写码。
4. **复杂游戏私有协议交给游戏开发者**，适配器只实现标准化调用接口，不改 Croupier 核心。
5. **Agent 承担探测执行与进程管理**；**Server 负责配置、授权、调度、结果聚合**；Server 自身依赖探测仍复用同一套内核。
6. **先完成一个参考适配器与完整契约测试**，再考虑分发、签名、WASM 等扩展机制。

**优先落地项**（原文判断）：不是写更多探测器，而是先把 `croupier-probe-jsonl-v1` 这个外部调用契约**定义完整**——启动握手、请求与响应、取消、崩溃恢复、版本兼容、凭证传递、安全约束。契约稳定后 Go Agent 才能可靠调用第三方探测程序。

## 核验与采纳判定（本仓 2026-10-14）

| 主张                          | 判定                 | 说明                                                                                                     |
| ----------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------- |
| 不用 Go `plugin`              | **采纳**             | 与本仓「core 包零外部依赖」约束一致；且同进程插件故障隔离差、多语言不支持                                |
| 独立进程 + JSONL IPC          | **采纳，待契约细化** | 契约字段与生命周期是本设计的核心交付，未定义前不算完成                                                   |
| 内置通用探测 + 声明式         | **采纳**             | 与第一份评审的 L1/L2 分阶段一致                                                                          |
| 复杂私有协议交给游戏开发者    | **采纳**             | 呼应用户「私有协议偏多」的现实，避免 Croupier 变成协议专家                                               |
| 「不要每次探测启动进程」      | **采纳为硬约束**     | 原文提及但未展开，进程复用方案**必须在设计中补齐**，否则探测周期被启动成本主导                           |
| `probe-adapter.yaml` 字段规范 | **待定**             | 原文自述字段规范待定；本仓 `ProbeTarget`（第一份评审提出）与本清单的关系需在设计中说清，**不许两套并存** |
| Server 负责结果聚合           | **采纳**             | 与用户 2026-10-14「结果需回流 server 做统计」一致                                                        |
