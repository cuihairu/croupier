# 高风险业务操作执行契约设计

日期：2026-10-17。状态：**待设计评审**。本页补齐
[游戏后台业务设计补齐清单](game-operations-design-plan.md) §3。评审通过前，本文只定义契约与验收，不修改
`TaskRun`、审批、执行日志或函数调用 wire，也不把所有业务函数强制升级为高风险操作。

## 1. 目标与范围

高风险业务操作指错误、重复、越权或范围漂移会造成资产、账号、订单、邮件、活动等不可逆影响的受控写操作。查询、只读探测、页面草稿保存不属于本文范围；发布、配置和批量任务可复用同一执行身份模型，但其专属流程另行细化。

设计目标：

1. 一次业务意图在整个链路中有稳定、可查询、可审计的身份。
2. 审批冻结实际参数、目标、预算和有效期，执行前不得被悄悄替换。
3. 游戏侧持久幂等，平台重试不造成重复发放。
4. 成功、失败、取消、结果未知语义可区分，不把未知自动改写为成功或失败。
5. 补偿、撤销、回滚显式建模，不承诺游戏已消费资产的通用回滚。

## 2. ID 与记录职责

| 身份/记录                   | 生成者与职责                                                                                                                                                       | 关系与不变量                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `operationId`               | 平台在创建业务意图时生成，代表一次具体业务操作。全局非空、不可变，推荐 `(gameId, env, domain, intentUUID)` 或等价规范编码；对玩家可见时显示短码，不暴露内部自增 ID | 同一 operationId 的实际目标、参数、预算摘要、函数契约指纹必须一致；改任一字段必须生成新 operationId 并重新审批 |
| `taskId` / `TaskRun.TaskID` | 任务执行实例 ID，负责进度、事件、取消、调度和恢复                                                                                                                  | 单对象操作允许 1:1；批次中一个任务包含多个逐对象 operationId。任务重启不能更换 operationId                     |
| `requestId`                 | 一次底层传输/函数调用尝试 ID，用于网络与插件排障                                                                                                                   | 同一 operationId 可有多个 requestId；requestId 失败或超时不代表业务失败                                        |
| `traceId`                   | 跨服务分布式追踪 ID                                                                                                                                                | 从发起、审批、任务到游戏调用尽量透传；OTel 关闭时仍保留在任务/执行日志中                                       |
| `IdempotencyKey`            | 平台向函数/任务层传递的幂等键                                                                                                                                      | 对高风险业务操作必须等于 `operationId`；不得使用页面刷新键、任务重启键或随机重试键                             |
| 审批记录                    | 保存申请者、审批者、状态、scope、函数、payload、任务关联和时间                                                                                                     | 审批 payload 必须包含 operationId 和请求摘要；批准结果不等于游戏执行成功                                       |
| `ExecutionLog`              | 保存请求/响应载荷级审查数据，并关联 scope、函数、页面、操作者、状态和 trace                                                                                        | 日志保留期可短于业务凭证；审计哈希链与任务/游戏凭据用于长期追溯                                                |
| 游戏执行凭据                | 游戏函数持久化幂等后返回，形式由函数契约定义                                                                                                                       | 凭据、operationId 和游戏侧结果必须可互相查询；凭据缺失时只能置为结果未知，不得伪造成功                         |

现有 `TaskRun`、审批模型和 `ExecutionLog` 已分别承载任务 ID、幂等键、审批 payload、trace、请求响应和 scope。实现是否新增列、新增凭据表或使用结构化响应映射，待评审选择；但无论落库形式如何，上述职责不得合并或省略。

## 3. 操作请求契约

创建高风险操作时，平台必须生成并持久化以下快照：

```text
BusinessOperationRequest:
  operationId
  gameId / env
  actor              # 发起人
  businessDomain     # asset/mail/ban/payment/activity/...
  operationType      # grant/deduct/send/ban/unban/...
  target             # 玩家身份与业务目标（引用第 5 项身份模型）
  parameters         # 实际执行参数，含币种/物品/数量/期限/原因/文案等
  budget             # 人数、件数、金额、费率、预算上限及币种
  preconditions      # 版本号、余额下限、状态、活动窗口、区服等
  functionRef        # functionId、契约版本/指纹、SDK/插件版本
  approvalRef        # 审批流、审批快照摘要和有效期
  idempotency        # operationId、允许重试窗口、过期策略
  compensation       # 是否支持撤销/冲正/补偿及游戏侧能力声明
```

快照在提交审批前生成。审批人看到的是该快照的摘要；批准后平台不得用前端重新填写的表单值替换快照。执行时以快照为准，页面版本、菜单标签、表单默认值变化不改变业务请求。

### 3.1 参数与目标摘要

- 参数摘要至少包含规范化 JSON、字段 schema 版本和敏感字段脱敏规则；哈希用于快速比对，不能替代原文快照。
- 目标摘要包含账号、角色、区服、渠道/平台、外部 ID 与显示名。列表或筛选条件不能只写 SQL/过滤器，必须物化执行时的对象集合或对象集指纹（批量语义见第 4 项设计）。
- 预算摘要必须写清计数口径和上限，例如“目标 100 人、每人 100 金币、总上限 10000 金币”；不含上限或币种的摘要不得通过审批。
- 审批页面需同时展示 PageSpec/合同摘要与业务快照摘要，两个摘要都要带版本。

### 3.2 合同版本与前置条件

执行前必须重新检查：

1. 操作者仍有函数权限，且未被禁用或调离审批角色。
2. `functionId`、函数契约版本/指纹、SDK/插件版本仍满足审批声明；不满足则阻断。
3. scope 仍是同一 `(gameId, env)`。
4. 审批未过期、未被撤销，工作流状态仍为 approved。
5. 目标版本、状态、余额、期限等前置条件仍满足；变化则要求重新审批。
6. 预算、速率和并发额度未超限。

PageSpec 发布快照负责“页面当时绑定哪个函数和表单”；业务审批快照负责“这次批准执行什么”。两者相互引用版本，但不能互相替代。

## 4. 游戏侧持久幂等

游戏函数必须把 `(scope, operationId, requestFingerprint)` 持久保存，并在执行任何业务副作用前完成判重：

1. **首次执行**：持久化请求指纹后执行；成功返回成功状态和游戏凭据；失败返回最终失败或可重试失败；无法返回时平台置结果未知。
2. **同 ID 同指纹重放**：无论游戏已成功或失败，直接返回首次结果和原凭据，不再次执行副作用。
3. **同 ID 改参数/目标/预算**：返回冲突，不得覆盖原请求；平台展示原快照并禁止复用 operationId。
4. **同 ID 超过保留期**：返回已过期冲突；平台必须生成新 operationId 并重新审批，不得把旧 ID 视为可继续执行。
5. **部分写入**：游戏侧事务无法覆盖所有副作用时，必须返回结果未知和可查询位点，而不是把本地部分成功包装成成功。

最低返回契约：

```text
GameOperationResult:
  operationId
  requestFingerprint
  outcome           # succeeded | failed | retryable_failed | unknown | conflict
  gameReceipt       # 游戏侧持久凭据；可按契约延后由查询补齐
  result            # 实际变更结果、余额/版本号/投递批次等
  retryableAfter    # 仅 retryable_failed/unknown 时可提供
  queryHint         # 查询函数/位点/窗口
```

游戏侧幂等存储必须与业务副作用在同一可靠存储中，不能只放在进程内存、Agent 离线缓存或平台执行日志中。若外部函数插件代理 HTTP 接口，插件必须声明该 HTTP 接口已实现持久幂等；否则不得注册为高风险写函数。

## 5. 执行状态机

```text
draft → pending_approval → approved → ready → dispatching
      → running → succeeded | failed | retryable_failed | unknown
                 \→ cancel_requested → canceled | cancel_failed

expired / rejected / blocked 可从等待或执行前状态进入；
succeeded / failed / unknown 为业务终态，只能被游戏查询结果修正，
不得因平台重启、日志清理或任务取消改变。
```

| 状态               | 语义                                                 | 允许动作                                             |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------------- |
| `succeeded`        | 游戏返回成功且有可追溯凭据，或结果未知后查询确认成功 | 只读查询；如需变更走补偿/撤销操作                    |
| `failed`           | 游戏明确返回最终失败，未产生业务副作用               | 修正原因后用新 operationId 重新提交审批              |
| `retryable_failed` | 游戏明确可重试失败，且未产生副作用                   | 在准入窗口内用同 operationId 重试                    |
| `unknown`          | 超时、连接断开、游戏返回不完整或部分写入             | 只允许同 operationId 查询/受控重试；禁止发放替代奖励 |
| `cancel_requested` | 平台请求取消，尚无游戏终态                           | 由游戏确认；未确认前不能宣称已撤销                   |
| `cancel_failed`    | 游戏拒绝取消或副作用已开始                           | 保持原操作结果；另行走补偿/撤销                      |
| `canceled`         | 游戏确认未产生副作用并已终止                         | 不可复用 operationId；重新执行需新审批               |

`ExecutionLog.Status` 当前只有 `ok/error`，适合载荷请求结果；业务终态必须保留在任务/业务操作记录或结构化响应中，不能把 `unknown` 简化为 `error`。

## 6. 重试、取消、撤销与补偿

### 6.1 重试准入

- 只允许平台自动重试 `retryable_failed` 或 `unknown`，且必须复用 operationId 和原快照。
- 游戏明确 `failed`/`conflict`、审批过期、函数契约变化、目标版本变化、预算超限时禁止自动重试。
- 重试必须受指数退避、最大次数、并发上限和游戏健康状态限制；达到上限后保持 `unknown` 并告警，不改判失败。
- 响应丢失后的重试依赖游戏持久判重；平台不得先标记失败再生成新 operationId 发放替代奖励。

### 6.2 取消边界

- 执行前可平台取消；已派发后必须发送游戏取消请求并等待确认。
- 游戏不支持取消、副作用已开始或批次已部分执行时，取消失败并逐对象保留原结果。
- 取消操作本身也要携带取消凭据，不得把“任务状态 canceled”解释为资产已回滚。

### 6.3 撤销、回滚与补偿

| 动作      | 语义                                              | 前提                                           |
| --------- | ------------------------------------------------- | ---------------------------------------------- |
| 撤销      | 游戏原生撤销原操作并恢复原状态                    | 函数声明支持且游戏校验目标未被消费             |
| 冲正/回滚 | 账务反向记录，不抹除历史                          | 游戏账务系统支持，不用于道具已消费场景         |
| 补偿      | 生成一笔新业务操作，引用原 operationId 和失败原因 | 需要新审批、新 operationId，并记录关联原因     |
| 人工处理  | 游戏侧处置后回填结果                              | 保留工单/审批/游戏凭据，不直接修改原始执行状态 |

平台不提供通用“一键回滚”。是否可撤销由游戏函数能力声明，执行时由游戏做最终判断。

## 7. 权限与审批冻结

1. 高风险函数契约必须声明资源、操作类型、是否需要审批、预算字段、敏感度和补偿能力；注册时不满足最低声明则拒绝进入高风险执行目录。
2. 审批上下文包含：操作者、审批工作流版本、operationId、请求快照哈希、PageSpec/合同版本、有效期和重试窗口。
3. 审批人必须与发起人隔离，并具备目标 scope 权限；代理审批必须保留委托关系。
4. 审批通过后，请求快照哈希、目标集指纹、预算上限、合同指纹和有效期写入执行上下文；任何一项不匹配即 `blocked`。
5. 审批后增加目标、修改数量、修改文案、修改区服、换函数或换插件版本都必须重新审批；减少目标或预算也需重新审批，避免用“缩小”掩盖操作意图变化。
6. 审计必须记录发起、审批、执行、重试、取消、补偿和结果收敛，至少关联 operationId、taskID、审批 ID、traceId 和游戏凭据。

## 8. 凭据查询与结果收敛

- 函数契约必须提供按 operationId/游戏凭据查询结果的只读能力，或声明游戏事件回调如何补齐凭据。
- 平台可在 `unknown` 后周期查询；查询成功、失败或冲突即按游戏结果收敛，查询无结果在保留期内不能推断失败。
- 事件回调必须签名验证、去重、限定 scope，并与 operationId/凭据匹配；不能仅凭未收到事件判定失败。
- 凭据展示需脱敏，但操作者和审计员必须能追溯完整凭据的受控查询路径。
- 日志清理不得成为结果未知的原因；长期业务结果和凭据必须存放在符合保留期的业务任务/审计存储中。

## 9. 验收场景

1. **响应丢失不重复发奖**：游戏已入账但 HTTP 响应丢失，任务为 `unknown`；同 operationId 重试被游戏判重并返回原凭据，最终收敛成功，只发放一次。
2. **同 ID 改参数拒绝**：同 `(gameId, env, operationId)` 修改金额、目标、预算或函数版本，游戏与平台均返回冲突，原快照不变。
3. **审批后范围变化拦截**：审批通过后目标集指纹、余额版本、活动窗口或合同指纹变化，执行前进入 `blocked`；需要重新提交并重新审批。
4. **结果未知不被误判**：超时和部分写入均保持 `unknown`；超过自动重试上限后只告警和允许查询，不生成替代奖励。
5. **取消不虚构回滚**：游戏已发放后取消返回 `cancel_failed`，操作保持游戏结果；如需恢复只能走显式撤销/补偿并再次审批。
6. **追踪链完整**：从页面、审批、任务、执行日志、审计到游戏凭据可按 operationId 串联；OTel 关闭时仍可依靠持久 ID 与凭据审计。
7. **过期不复活**：operationId 超过游戏保留期后重放返回过期冲突；重新执行生成新 operationId 并走新审批。

## 10. 待评审决策

1. `operationId` 的具体编码、最大长度、前缀规范和跨游戏唯一性口径。
2. 游戏凭据的存储形式：扩展 `TaskRun`/`ExecutionLog`、新增业务操作表，还是统一结构化 `ResultPayload`。
3. 各游戏函数 SDK 是否统一内建 `GameOperationResult` envelope，外部函数插件如何声明兼容。
4. `unknown` 的默认自动查询频率、重试上限、保留期和告警级别。
5. 取消协议是否作为最低接入能力，还是仅对支持取消的函数开放。
