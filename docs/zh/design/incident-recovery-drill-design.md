# 事故关联与恢复演练

## 状态与范围

- 状态：设计待评审；`incidents` 是事故真值，`alerts/execution_logs/audit_records` 是证据源，备份与恢复是演练对象。
- 目标：告警、操作、受影响对象、版本与恢复动作能互查；平台数据库恢复和游戏数据恢复分开定责，告警恢复不等同数据恢复。
- 现状：`Incident` 已有 `GameID/Env/ExecLogIDs/RefType/RefID/Details`；`ExecutionLog` 已有 scope、function、actor、status 和 `TraceID`；`AuditRecord` 有 actor/resource/context/hash chain；`GameRelease`、`ConfigVersion`、supervisor 事件和插件/函数版本可提供变更快照；备份记录已有 checksum/status/location，CDC journal 可顺序回放且要求事务边界。

## 关联维度与真值

| 维度        | 真值/来源                                          | 关联规则                                 |
| ----------- | -------------------------------------------------- | ---------------------------------------- |
| scope       | Incident/Alert/ExecutionLog/审批的 `gameId/env`    | 非空必须相等；平台级 scope 单独标记。    |
| 业务目标    | 统一目标引用                                       | 保存稳定 ID 和 `identityFingerprint`。   |
| operationId | 高风险契约、审批、任务、执行日志、游戏凭据         | 作为跨系统查询键，不重生成。             |
| 任务/审批   | `TaskID`、审批 ID                                  | 保留申请/批准范围快照。                  |
| trace       | `ExecutionLog.TraceID`、AuditContext、OTel         | OTel 关闭仍保留持久 trace 字符串。       |
| Agent       | AgentID、`agentVersion`、二进制指纹                | 从注册、心跳、supervisor 事件/快照读取。 |
| 插件/函数   | manifest/contract 版本与摘要                       | 与执行时快照绑定。                       |
| 游戏/配置   | GameRelease、ConfigVersion、发布状态与指纹         | 与事故时间窗对齐。                       |
| CDC         | source ID、位点、journal 事件 ID、事务 ID、规则 ID | 只保存引用和哈希，不复制敏感 row image。 |

事故详情保存“证据引用 + 摘要”，不把完整请求/响应、凭据或玩家敏感载荷复制进 Incident。读取时按权限逐源展开。

## 事故入口与查询

1. 自动转换：alert、probe window、supervisor event、cicd build、CDC 规则命中和受控操作异常都可转 Incident；转换幂等键由源类型、源 ID 和事件指纹组成。
2. 关联查询：以 Incident 为根展开审批、操作、任务、Agent/插件/游戏/配置版本、告警和 CDC 窗口；每个引用记录抓取时间，避免事后真值变更导致解释漂移。
3. 归因：`ResponsibleType=change` 时必须绑定发布/配置/进程更新/插件变更 ID；不能仅用时间先后归因。
4. 恢复状态：Incident 的 resolved 只表示人工闭环；`data_recovered`、`game_side_effect_closed`、`cdc_replay_closed` 是独立布尔/状态，缺失即 `unknown`。
5. OTel 裁剪：不生成 span，但 `traceId`、operationId、任务/审批 ID、凭据和审计链仍写库；面板显示“无完整链路视图，可用持久 ID 查询”。

## 备份责任矩阵

| 对象         | 平台责任                                       | 游戏/外部责任                            |
| ------------ | ---------------------------------------------- | ---------------------------------------- |
| meta 数据库  | 内置逻辑备份、checksum、恢复演练               | 承接外部 PITR/快照（如选用）。           |
| game 数据库  | 不默认掌握游戏业务真值；可执行 dump/记录元数据 | 备份策略、点恢复、合规保留和数据一致性。 |
| 平台配置     | 配置版本、last-good、制品 checksum             | 外部 IaC/发布系统自行备份其状态。        |
| Agent 运行态 | supervisor/审计/配置 last-good                 | 本机日志与崩溃产物按保留策略保存。       |
| CDC journal  | 位点、事务边界、事件哈希、容量与损坏检测       | 源库备份、schema 历史和逻辑快照。        |
| 告警 spool   | 持久待发、重试计数、顺序与去重键               | 外部告警系统保证其接收端状态。           |

平台不得宣称能恢复它不拥有的游戏数据库业务真值；未接入备份的数据源必须在计划中显示 `not_covered`。

## 恢复顺序

```text
隔离环境建立 → 平台 meta/配置恢复 → 版本兼容校验 → Agent/插件重注册
→ 数据恢复（game DB/CDC）→ 一致性验证 → 任务收敛 → 运行恢复
```

1. 平台先恢复到与二进制/迁移兼容的快照；新旧二进制兼容规则沿用版本化迁移门槛。
2. Agent 恢复后用旧配置 last-good 和指纹校验；配置或制品与恢复版本不一致时进入人工核对。
3. 游戏数据库按其 RPO/RTO 恢复；平台只记录恢复点、校验结果和责任方。
4. CDC 从 journal 或 source 位点恢复，优先满足完整事务边界与快照早于起点；缺事务元数据必须拒绝恢复。
5. 告警 spool 恢复后按原顺序重放；已确认/已恢复的告警不重复升级。
6. 运行恢复前执行一致性核对：审计链、任务终态、审批、游戏凭据、版本指纹和恢复点清单。

## 恢复后任务与凭据

- 状态 `succeeded` 且已有游戏凭据：不重放，只核对业务真值。
- 状态 `unknown`：只能用原 `operationId` 查询游戏结果；查到副作用则收敛终态，查不到也禁止替代补偿。
- 状态 `retryable_failed`：恢复后按原快照和窗口重试；契约、目标或预算变化必须重新审批。
- `canceled/failed`：不得复活旧任务；补偿生成新 operationId、新审批和新目标快照。
- 平台库恢复点之后产生的任务，即使运行日志存在，也标记 `orphaned_execution` 并人工核对，不自动当作可信成功。

## 演练设计

| 演练           | 输入                              | 成功标准                                                         |
| -------------- | --------------------------------- | ---------------------------------------------------------------- |
| 审计链闭环     | 错误补偿 + 告警 + 审批 + 执行日志 | 能还原操作者、批准范围、目标指纹、版本和游戏凭据。               |
| 平台库恢复     | meta dump + 同版本二进制          | healthz、登录、函数目录、审批/审计链可查，恢复点后记录标记孤儿。 |
| Agent 恢复     | 配置 last-good + 指纹 + 崩溃产物  | 注册成功、supervisor 事件可追、配置版本无静默漂移。              |
| CDC 恢复       | journal + 一致快照                | 事务完整、按序、目标幂等；缺标记场景被拒绝。                     |
| 告警恢复       | 持久 spool + 旧告警状态           | 不重复升级，顺序不乱，已恢复告警不 reopen。                      |
| 结果未知收敛   | 响应丢失 + 游戏凭据查询           | 只查原 operationId，不重复发奖，unknown 不被伪造成功。           |
| 不可逆变更失败 | 数据库迁移 + 备份点               | 不自动回滚不可逆迁移；给出恢复点、前滚路径和人工决策记录。       |

演练必须在隔离环境、独立 scope、同版本或声明的混合矩阵下执行；生产演练只能只读核对。

## 保留与权限

| 数据          | 建议热保留     | 长期锚点                            |
| ------------- | -------------- | ----------------------------------- |
| ExecutionLog  | 30–90 天       | operationId、凭据、审计哈希、摘要。 |
| 审计记录      | 按合规期限     | hash chain + 签名。                 |
| CDC journal   | 按恢复窗口     | source 位点、事务 ID、事件哈希。    |
| 告警/通知     | 90 天          | dedup key、状态迁移和升级记录。     |
| 崩溃产物/录像 | 14–30 天       | 指纹、 Incident 引用、访问审计。    |
| 恢复演练报告  | 永久或合规期限 | 版本、快照 ID、RTO/RPO 和缺口。     |

具体天数由部署合规策略覆盖；本页默认是上限和最小查询锚点。敏感载荷默认脱敏，读取原文需专门权限并二次审计。

## 验收场景

1. 错误补偿告警可在 5 层内查到操作者、审批范围、实际 `role/server`、operationId、游戏凭据、游戏/配置版本和 Agent 指纹。
2. 从 meta 备份恢复平台后，恢复点前的审批/审计链完整；恢复点后孤儿任务明确可见且不重放。
3. 游戏库恢复到备份点后，`unknown` 操作按原 operationId 查询：游戏已入账则收敛成功，未查到则保持 unknown，不补偿。
4. CDC journal 缺事务结束标记时恢复拒绝；完整 journal + 一致快照可按序回放且重复回放不重复生效。
5. Agent 恢复后使用旧指纹失败，进入人工核对；使用匹配指纹后自动注册并保留事件链。
6. 告警 spool 重放不产生重复 critical 升级，已 resolved 的源告警不会被旧数据 reopen。
7. OTel 关闭时，审计报告仍能按 operationId + traceId + 审批/任务/凭据还原关键链路。
8. 不可逆迁移失败时，系统给出备份点、前滚路径、影响对象和人工决策记录，不自动回滚。

## 落地批次

1. Incident 增加统一恢复状态、版本指纹引用和孤儿任务标记；先补模型与查询测试。
2. 事故详情新增证据聚合 API，按权限逐源返回审批/任务/执行/版本/Agent/CDC 引用。
3. CDC 恢复协调接入 Incident，记录恢复计划、审计 ID、拒绝原因和闭环状态。
4. 恢复演练 runner 先支持平台 meta 与 Agent 配置只读校验，再扩展隔离库。
5. 面板提供恢复时间线、缺失证据、未知结果和人工决策入口。
