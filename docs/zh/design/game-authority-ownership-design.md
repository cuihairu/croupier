# 游戏数据权威归属设计

日期：2026-10-17。状态：**待设计评审**。本页补齐
[游戏后台业务设计补齐清单](game-operations-design-plan.md) §2 的数据归属、读写入口、副本时效与存量
`Player/Balance` 收口方案。评审通过前，本文只定义边界，不授权重构本地表、新增游戏经济系统或迁移数据。

## 1. 设计原则

- 游戏服务是玩家运行态、角色、资产、封禁、订单到账、邮件、活动生效状态的权威。Croupier 是操作面，不成为游戏业务真值源。
- Croupier 的权威数据限于平台控制面：函数契约、函数安装与版本下限、页面与菜单、权限、审批、任务执行记录、执行日志、审计、发布快照、探测结果和配置版本。
- 每个游戏业务读模型必须声明 `sourceSystem`、读取入口、采集时间、数据时效与失败展示方式。未声明或过期时显示不可用，不把空值、旧副本或平台默认值渲染成真值。
- 每个游戏业务写操作必须通过游戏函数/插件执行。Croupier 本地事务成功只代表操作意图或控制面记录成功，不得合并为游戏执行成功。
- 所有读写与执行记录都限定 `(gameId, env)`。游戏函数契约必须声明目标数据域和业务目标；平台不猜测区服、角色或账号。

## 2. 权威系统与读写矩阵

下表是接入契约的最小字段要求。`权威` 回答“冲突时以哪边为准”；`Croupier 副本` 只在显式接入后存在。

| 业务域           | 权威系统与写入入口                                                                       | Croupier 读取入口                                                        | Croupier 副本与时效                                                            | 恢复责任                                                                              |
| ---------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 玩家账号与登录态 | 游戏账号服务。创建、资料、改密、登录态维护只能调用游戏函数；账号服务可回调 Croupier 审计 | 查询函数返回账号标识、角色摘要、状态、资料版本与采集时间                 | 不持久化密码、令牌或完整账号资料；只允许短 TTL 查询结果或审计摘要              | 游戏账号服务负责账号恢复；Croupier 仅恢复审批、执行记录和审计                         |
| 玩家角色与进度   | 游戏角色服务。建角、改名、等级、VIP、区服迁移由游戏函数写                                | 查询函数返回 `gameId/env/zoneId/playerRef`、角色状态、版本号和采集时间   | 不建通用角色副本。工作台可保存执行对象快照用于审计，不用于实时展示覆盖真值     | 游戏侧备份恢复角色；Croupier 恢复操作对象快照与执行历史                               |
| 资产与货币余额   | 游戏资产账务系统。发放、扣除、冻结、补偿一律通过带游戏侧凭据的函数                       | 查询函数返回余额、资源项、账务版本号、采集时间和查询凭据                 | 不以平台表为余额真值；补偿/邮件对象快照可记录预期变更，不能视为已到账          | 游戏账务系统负责对账、补偿与回滚；Croupier 保留意图、审批和执行凭据                   |
| 封禁与处置       | 游戏风控/账号服务。封禁、暂停、解封通过游戏函数写，并返回处置凭据                        | 查询函数返回处置状态、原因、期限、生效时间和凭据                         | 审批与执行日志保存对象快照、操作原因和结果；不把平台字段当长期封禁真值         | 游戏侧恢复处置状态；Croupier 恢复历史以便追溯                                         |
| 订单与到账       | 支付渠道持有渠道订单；游戏支付/账务服务持有到账状态。补单函数是唯一受控写入口            | 渠道订单、游戏订单和到账结果分来源查询；每条记录带来源、交易号和采集时间 | 不在平台重建订单总账；核查页可暂存查询快照用于跨来源比对                       | 渠道与游戏各按其账务恢复；Croupier 恢复核查记录、审批、任务和执行日志                 |
| 邮件与补偿投递   | 游戏邮件/补偿服务。创建、撤回、领取和失败重投通过游戏函数；领取结果由游戏事件或查询返回  | 查询函数返回投递状态、领取状态、目标、批次、游戏凭据和时间               | 平台可保存任务、逐对象结果、失败清单和最后查询时间；副本不驱动到账判断         | 游戏服务恢复邮件；Croupier 恢复任务状态和可重放审批上下文时必须重新执行游戏侧前置检查 |
| 活动与运营配置   | 游戏活动运行时。配置解析、定时生效、灰度、回滚和玩家可见状态由游戏执行                   | 查询函数返回活动配置版本、发布批次、生效范围、游戏侧状态和采集时间       | PageSpec 只存页面表现；平台任务/审批存发布意图和对象范围，不替代活动运行时状态 | 游戏侧备份与版本化配置负责活动恢复；Croupier 恢复发布记录，重放前重新校验版本与范围   |

读取入口统一通过已注册、已授权的游戏函数或外部函数插件，不新增直连游戏库的通用查询通道。查询函数契约必须包含数据域、目标、返回字段、敏感字段策略、缓存时效和错误码；无法查询时页面显示来源与时间，而非伪造空对象。

## 3. 副本、快照与缓存时效

| 类型            | 用途                                 | 生命周期与失效                                                                        | 冲突规则                                              |
| --------------- | ------------------------------------ | ------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 短 TTL 查询结果 | 工作台、订单核查等展示               | 默认不持久化；如需持久化，写入 `fetchedAt` 和 `expiresAt`，读取时过期即标红或重新查询 | 只作为展示缓存，不参与业务判断                        |
| 审批对象快照    | 证明审批时看到的人/角色/资产/预算    | 审批通过后不可修改；执行时保留原快照并记录实际执行返回                                | 实际对象或版本变化时阻断执行并要求重新审批            |
| 任务逐对象结果  | 批量补偿、邮件、封禁的进度和故障恢复 | 按任务保留，包含游戏凭据、状态、失败码和时间                                          | 以游戏查询/回执为准；平台重复记录必须能被凭据去重解释 |
| 执行日志与审计  | 追溯意图、请求响应、操作者和 trace   | 按 Croupier 保留期清理；敏感载荷脱敏                                                  | 不作为游戏业务真值，冲突时优先游戏侧查询/凭据         |
| 探测与健康结果  | 网络与服务可用性判断                 | 按探测窗口保留                                                                        | 不用于判定资产或订单业务结果                          |

所有副本写入必须能回答：数据来自哪个 `sourceSystem`、哪个函数、哪个 `operationId`/凭据、哪个 `(gameId, env, 业务目标)`、何时采集、何时失效、谁授权。缺少其中任一项的持久化副本不满足本设计。

## 4. 存量本地 `Player/Balance` 定位

### 4.1 当前代码事实

- `internal/model/player.go` 定义 `Player`，包含 `Username/Nickname/Email/Phone/GameID/Status/Balance/Level/VIP/Password`；`Status` 直接表达 active/banned/suspended，`Balance` 表示游戏货币。
- `internal/model/player_model.go` 提供 `Create/FindOne/FindByUsername/Update/Delete/List` 等通用读写，`UpdateBalance` 在本地事务中累加余额并拒绝负余额，`BanPlayer/SuspendPlayer/ActivatePlayer` 直接更新本地状态。
- `internal/handler/routes.go` 注册玩家路由，包含创建、更新、删除和 `POST /:id/balance`。
- `internal/model/migration.go` 将 `Player` 放入每个 `(gameId, env)` 的 game database 模型集合；没有区服、大区、渠道、平台、角色映射和外部玩家 ID 字段。
- 执行日志 `ExecutionLog` 已记录 `gameId/env/functionId/actor/status/traceId/requestPayload/responseBody`，但没有业务 `operationId` 和游戏执行凭据字段。本设计不修改日志 wire，第 3 项执行契约文档需定义扩展或映射方案。

因此，本地表实际承载的是平台内置玩家资料和本地状态/余额模型；仓库内没有证据证明它自动映射任一真实游戏资产。不能简单删除旧表，也不能继续把 `UpdateBalance` 当作发放资产。

### 4.2 正式定位

1. 兼容期内本地 `players` 表定级为 **Croupier 本地演示/辅助账户模型**，不是游戏玩家、角色、资产或封禁真值。
2. `Password` 仅可用于平台演示登录或本地扩展的凭据校验；真实游戏登录凭证不得迁入、不得在日志和执行载荷中出现。
3. `Balance` 是本地模型字段，不代表游戏货币。任何真实补偿、发放、扣除必须改走游戏函数；禁止继续通过 `POST /:id/balance` 直接变更真实资产。
4. `Status` 是本地账户状态；真实封禁、暂停、解封必须经游戏函数并记录处置凭据。若游戏侧要求以本地字段加速展示，必须显式配置同步任务，并标注副本时效与冲突方向。
5. 玩家工作台可保留本地表作为历史/演示数据源，但 UI 必须区分「Croupier 本地模型」与「游戏权威查询」；未接入查询时不提供真实资产操作。

### 4.3 收口方案

| 阶段          | 目标                                                                                            | 边界与验收                                                                  |
| ------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| A. 冻结新依赖 | 新真实游戏页面和函数不再读写 `PlayerModel.UpdateBalance/BanPlayer/SuspendPlayer/ActivatePlayer` | 评审通过后用代码守卫和接入清单检查；不改旧页面行为                          |
| B. 标注来源   | 玩家列表/详情区分「本地模型」和「游戏函数」来源；本地资产写只保留演示模式或灰度关闭             | 默认生产 scope 不渲染本地余额为游戏资产；错误页说明游戏函数不可用           |
| C. 契约替换   | 建立账号、角色、资产、封禁查询/写函数契约；写入使用第 3 项 operationId 与游戏凭据               | 同一 operationId 在游戏侧幂等；响应丢失不得重复发放；离线失败可查询结果未知 |
| D. 数据映射   | 为每个游戏配置外部玩家/角色标识映射；本地 ID 只作 Croupier 引用，不当作游戏主键                 | 同一账号多角色、多区服可准确寻址；合服旧 ID 映射由游戏权威服务提供          |
| E. 历史收口   | 存量本地余额/状态迁移需按游戏生成对账报告，管理员确认后才切换显示与操作入口                     | 无对应游戏记录的数据保持本地归档；禁止自动把本地余额折算成游戏资产          |

不建议一次性删除 `players` 或 `UpdateBalance`：它被演示、测试和历史页面引用，直接删除会造成数据与页面断裂。收口以禁用真实写路径、显式来源和契约替换为目标。

## 5. 离线、失败与恢复

1. **查询失败**：返回来源级错误与最后可用时间；不返回零余额、未封禁或空活动等默认值。跨来源查询时逐来源标注成功/失败。
2. **写前失败**：游戏函数不可达、凭据缺失、契约版本不匹配或审批过期时拒绝提交，不写“已发放”。
3. **结果未知**：超时、连接断开或响应丢失必须进入 `unknown`，只能通过查询函数或游戏回执收敛。平台重试必须携带同一个业务 `operationId`；游戏侧凭据是判重的第一依据。
4. **部分成功**：批量/多步骤操作逐对象记录状态；不能把批次失败写成全部失败，也不能把平台记录成功写成资产已到账。
5. **补偿边界**：游戏道具已领取或消费时拒绝通用回滚；只能根据游戏侧提供的补偿或冲正函数执行，且必须再次审批并保留原凭据。
6. **恢复顺序**：先恢复游戏权威服务，再恢复 Croupier；平台副本启动后进入 stale 状态，重新查询确认后才可参与操作展示。不能反向用副本覆盖游戏数据。

## 6. 验收场景

1. **来源可见**：查询玩家资产返回资产值、`sourceSystem`、游戏函数/数据源、采集时间和 TTL；缓存过期时 UI 显示过期而非冒充实时值。
2. **受控写**：发起补偿生成业务 `operationId`，审批快照包含对象、参数和预算；游戏函数返回凭据后，执行记录、审计和任务结果均可通过同一凭据串联。
3. **响应丢失**：调用超时后任务状态为结果未知；操作者重试不产生第二个 operationId，游戏查询确认首次已入账后收敛为成功，不重复发放。
4. **游戏离线**：查询显示失败来源，写操作拒绝提交；已提交但结果未知的操作不能被标记成功，恢复后必须通过游戏查询或回执定案。
5. **本地表隔离**：生产 scope 的本地余额不显示为游戏资产；直接调用本地余额写接口不改变游戏真值，且新真实业务接入评审能拒绝该路径。
6. **副本不覆盖真值**：手工篡改或延迟的平台副本与游戏查询冲突时，页面和任务状态以游戏查询/凭据为准，并记录冲突。

## 7. 待评审决策

1. 本地 `players` 的演示/历史数据保留期，以及是否为旧工作台增加只读归档模式。
2. 游戏执行凭据是扩展 `ExecutionLog` 字段、写入结构化响应约定，还是新增凭据表；该决策与第 3 项执行契约联动。
3. 不同游戏的账号/角色/资产查询函数最小必填契约和错误码集合。
4. 每个数据域的默认查询 TTL、批量任务结果保留期和敏感字段脱敏策略。
5. 真实游戏接入方是否允许平台持久化任何业务副本；默认建议只持久化审计快照与任务结果。
