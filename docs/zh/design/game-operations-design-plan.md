## 2. 游戏数据权威归属

**已观察事实**：`internal/model/player_model.go` 存在本地 Player 读写、余额修改与封禁状态更新；当前仅据此不能判定该数据是否对应真实游戏资产。Core/Extension Mapping 已提出业务能力通过扩展交付，边界需进一步落实。

**建议方案**：逐项标注账号、角色、资产、封禁、订单、邮件与活动数据的权威系统、读写入口、同步方式、缓存时效及恢复责任；建议由游戏保存游戏业务真值，Croupier 保存操作意图、凭据、审计及必要查询副本，具体例外必须显式声明。

**需要定稿**：本地 Player/Balance 的正式定位、数据映射、离线查询标注、并发版本检查、读后验证与失败补偿；不能简单删除现有模型或把本地写成功当作游戏执行成功。

**验收场景**：一次资产查询能展示来源与采集时间，一次资产修改能关联游戏返回的凭据；游戏不可达时不返回伪造成功，副本不能覆盖业务真值。

## 3. 高风险操作执行契约

**既有能力**：平台已有幂等、审批、任务、审计与发布快照；[执行主路径](../architecture/data-flow.md) 已冻结页面绑定契约，下面要求补齐业务执行语义，不重新定义页面契约。

**需要定稿**：业务级 operationId 与 taskId/requestId/traceId 的关系、参数与对象摘要、游戏侧持久去重和过期策略、原请求冲突校验、执行凭据查询、重试准入、取消边界以及成功/失败/结果未知的区分。

审批应能冻结本次操作的实际对象、参数、预算和有效期，并在执行前重新检查权限、合同版本及前置条件；审批页面绑定快照与审批一次具体业务操作各自负责什么，要明确写出。

撤销、回滚与补偿分别建模；游戏道具已领取/消费时不能承诺通用回滚，结果未知不得自动变成失败并重新发奖。

**验收场景**：游戏已发奖但响应丢失，重试/查询不重复发奖；相同 operationId 改参数拒绝；审批后更换对象范围或超出预算拒绝；取消已完成任务不宣称撤销资产。

参考：[PlayFab 幂等与重试契约](https://learn.microsoft.com/en-us/xbox/playfab/economy-monetization/economy-v2/tutorials/idempotent-transactions-and-retries)；参考其职责划分，不复制具体保留期限。

## 4. 批量运营与补偿

**建议复用**：将批量运营作为现有异步任务上的业务执行方案，优先服务邮件、补偿和批量封禁，通过业务扩展提供页面。

**需要定稿**：圈选条件与排除条件、执行对象快照、重复对象处理、预演人数及资产总额、审批摘要、单批额度、并发/速率、失败停止阈值、逐对象 operationId、任务断点、暂停/恢复与最终核对。

对象名单若随时间动态变化，需明确何时冻结及审批后是否重新计算；预演必须说明是否调用游戏验证、是否产生副作用及有效期，禁止用前端计数替代后端快照。

**验收场景**：对固定目标集运行补偿，故障后恢复只执行未完成项，完成/失败/结果未知逐项可查，统计总额与游戏凭据一致；修改名单须重新审批。

## 5. 玩家身份与业务目标

**约束**：沿用 [scope 规范](../architecture/game-environment-scope.md)，gameId/env 表达隔离边界，区服/角色/渠道表达业务目标，不把物理服务器或渠道塞进 env。

**需要定稿**：账号与角色的区别、一账号多角色、区服/大区/渠道/平台标识、合服后的标识映射、外部账号映射、旧 ID 保留与无歧义寻址；字段按游戏能力选用，不强制所有游戏具备相同世界模型。

统一的目标引用应能被函数、任务、审批、工单、审计及探测关联；目标展示与实际执行引用一致，不能把昵称当稳定身份。

**验收场景**：两个区服存在相同角色 ID、一个账号有多个角色、合服前后存在旧 ID 时均能准确定位且不越 scope。

## 6. 游戏维护与发布

**既有能力**：版本记录、配置、supervisor 进程更新及 synthetics 规划可复用；进程启动成功不自动代表游戏业务已恢复。

建议流程：

```text
预检 → 发布公告 → 限制新登录/分配 → 等待保存/安全退出
→ 备份与更新 → 协议/业务探测 → 小范围开放 → 全量恢复
```

**需要定稿**：真实在线人数来源、维护与排空条件、超时和人工干预、区服批次、版本/配置/数据库兼容矩阵、开放闸门及失败处置；存在不可逆数据变更时明确禁止自动回滚和可用恢复路径。

复用现有任务执行与审批机制，不默认引入新的通用工作流引擎；平台控制哪些步骤、游戏自行实现哪些步骤、外部发布系统承担哪些步骤需逐项分工。

**验收场景**：维护中不提前开放新登录，新版本仅进程正常但登录探测失败时不开放；变更涉及数据库时能按兼容规则选择回滚、继续修复或恢复。

参考：[Agones Fleet Updates](https://agones.dev/site/docs/guides/fleet-updates/) 的游戏配合优雅退出机制；本项目不因此承诺集成 Agones。

## 7. 游戏接入与兼容性

**需要定稿**：SDK/OpenAPI/外部函数插件各自适用场景、最小必需能力、可选能力及未支持状态；参考游戏服务和明确的接入步骤，不把插件元数据当作业务已接入。

兼容矩阵包括平台、SDK、Agent、插件契约、函数契约与已发布页面版本；复用现有版本门槛和 stale 检查，明确升级顺序、混合版本、协议不兼容、回退及诊断方式。

验收工具应覆盖注册、schema、scope、授权、业务调用与去重、结果未知查询、断线恢复、任务取消及探测故障；外部插件优先使用 Go/Python 参考实现，其他语言按实际接入补充。

**验收场景**：开发者通过接入清单完成一个游戏的查询和受控写操作，错误 scope/旧契约/不支持能力给出可定位错误，SDK 路径与外部适配路径的额外跳转及耗时可观测。

## 8. 事故追踪与恢复

**建议关联维度**：gameId/env、业务目标、operationId、任务/审批/trace、Agent 身份、二进制指纹、插件版本、游戏版本及配置版本；各系统沿已有真值关联，不重复复制完整敏感载荷。

**需要定稿**：从告警到发布/操作/受影响对象的查询路径，游戏资产与平台数据库的备份责任、恢复顺序和目标时限，CDC 位点/规则窗口与待发告警恢复，恢复后的任务与凭据重放规则，日志/录像/凭据保留周期及权限。

OTel 关闭或构建裁剪时，基本操作凭据与审计仍可追踪；恢复演练使用隔离环境，明确哪些外部系统数据无法由平台恢复，不把告警恢复自动当成数据恢复完成。

**验收场景**：一次错误补偿可从告警定位操作者、批准范围、实际执行对象及版本；从备份恢复平台并恢复 Agent 后，不重复发奖，能够识别结果未知项和需要人工核对的记录。
