# 批量运营与补偿设计

日期：2026-10-17。状态：**待设计评审**。本页补齐
[游戏后台业务设计补齐清单](game-operations-design-plan.md) §4，建立在
[高风险业务操作执行契约设计](high-risk-operation-contract-design.md) 之上。评审通过前，本文不修改
`TaskRun/TaskEvent` 结构，不新增批次表，也不实现邮件、补偿或封禁页面。

## 1. 目标与范围

批量运营把一个已审批的业务意图应用到固定对象集，并为每个对象保留可恢复、可核对、可审计的执行单元。首期适用：

- 邮件与补偿：向多名玩家发放货币、道具、邮件附件或补偿包。
- 批量封禁/解封：对多个账号或角色执行处置。
- 批量订单补单：仅当支付/游戏函数支持逐单幂等和到账核对时启用。

不把平台变成游戏账务系统，不提供绕过游戏函数的批量数据库写入，也不用一个批次任务的成功状态替代游戏侧逐对象结果。

## 2. 批次身份与对象快照

### 2.1 身份模型

```text
BatchOperation:
  batchId             # 平台批次 ID，不可变
  parentOperationId   # 可选：事故/上游原因
  gameId / env
  actor / approver
  businessDomain
  operationType
  functionRef         # functionId + 契约版本/指纹
  selectionSnapshot
  executionPolicy
  budgetSnapshot
  approvalRef
  createdAt / frozenAt / expiresAt

BatchItem:
  batchId
  itemIndex           # 冻结名单内稳定序号
  operationId         # 每对象唯一业务操作 ID
  targetSnapshot
  parametersSnapshot
  state
  attempts / lastAttemptAt
  gameReceipt / resultFingerprint
  failure / queryHint
```

`batchId` 负责整批意图、审批和断点；`operationId` 负责每个对象的游戏侧幂等和凭据。二者都不能在重试、恢复或任务重启后改变。

### 2.2 对象冻结

圈选结果必须在提交审批前冻结为对象快照，至少包含：

- 稳定身份：账号 ID、角色 ID、区服/大区、渠道/平台、外部映射 ID。
- 展示信息：昵称、等级、VIP、状态等，仅用于审批者识别，不作为执行身份。
- 目标版本：余额/状态/邮件资格/订单状态等游戏侧版本号或快照指纹。
- 执行参数：每对象金额、物品、期限、原因、文案及其指纹。
- 排除原因：黑名单、风控、重复、余额不足、状态不满足等。

禁止审批时只保存筛选条件。若业务允许动态名单，必须明确冻结时点并在审批摘要中展示查询时间、数据源和过期时间；审批后重新计算、增删目标或改变排序都生成新批次并重新审批。

### 2.3 重复对象

1. 以规范化业务目标 + 执行参数作为去重键，而不是昵称、行号或前端选择集。
2. 同一批次重复目标在冻结阶段合并或拒绝；合并时必须保留参数一致，并记录对象出现次数。
3. 跨批次重复执行不由平台去重，除非函数契约提供按业务键查询的能力；否则只能通过风控/审批策略提示风险。
4. 同一账号多角色必须按角色分别生成 item；仅当游戏函数明确账号级语义时才可合并。

## 3. 预演

预演是后端生成的不可变审计材料，不是前端计数。

| 阶段     | 必做动作                                                   | 副作用     |
| -------- | ---------------------------------------------------------- | ---------- |
| 数据圈选 | 按后端条件查询游戏/权威数据源，生成候选与排除清单          | 无         |
| 对象验证 | 调用游戏只读验证函数检查资格、状态、余额、收件能力、黑名单 | 无         |
| 汇总     | 计算目标人数、每人数量、总数量、金额/币种、失败/排除数     | 无         |
| 快照     | 保存对象、参数、目标版本、来源、查询时间和有效期           | 仅平台记录 |
| 冻结     | 提交审批时固化快照和预算摘要                               | 仅平台记录 |

预演结果有有效期。过期后执行前必须重新预演并重新审批；函数声明支持时可用游戏侧版本号做增量校验，但仍不得静默修改名单。

## 4. 预算、速率与并发

### 4.1 预算快照

预算在冻结时写入批次和审批上下文，至少包含：

- 对象数上限与实际数。
- 每对象数量/金额上限与实际值。
- 总数量/总金额上限与实际值，含币种和小数精度。
- 邮件/道具/封禁等类型计数。
- 单批与滚动窗口限额、审批例外编号。

执行器在每个 item 派发前做本地原子扣减，收到游戏终态后核对实际结果；游戏返回超出预算必须停止派发并告警。任何参数变化都要求新审批，不允许执行器自动“按剩余预算截断名单”。

### 4.2 速率与并发

执行策略必须显式声明并可被游戏能力约束覆盖：

- 全局并发、单游戏并发、单 Agent/插件并发。
- 每秒/每分钟请求数，批内突发窗口。
- 游戏健康探测门槛与熔断窗口。
- 单对象超时、批次总时限。
- 暂停冷却时间与恢复批次大小。

执行器不得同时持有多个同名批次执行代；恢复时先读取逐对象状态和游戏查询结果，再从第一个未终态对象继续，不能从头重放已完成项。

### 4.3 失败阈值

失败策略至少区分错误类型：

| 错误类别           | 默认动作                           |
| ------------------ | ---------------------------------- |
| 参数/权限/合同冲突 | 立即暂停整批，人工处理             |
| 目标资格变化       | 标记该对象 blocked，可继续其余对象 |
| 限流/暂时不可达    | 退避后重试，超过阈值暂停           |
| 游戏明确最终失败   | 记录失败并继续，达到阈值暂停       |
| 结果未知           | 停止新派发，优先查询收敛           |
| 预算/安全护栏超限  | 立即暂停并告警                     |

阈值必须写明分子分母，例如“连续 10 个失败或总失败率 20%”。默认暂停而非跳过，避免把风险隐藏为成功统计。

## 5. 执行与恢复状态

### 5.1 批次状态

```text
draft → previewing → pending_approval → approved → queued
      → running → paused | stopping
      → completed | partially_completed | failed | canceled | expired
```

批次终态只表示平台调度结束，不表示每个对象业务成功。终态摘要必须列出成功、最终失败、结果未知、阻断、取消的数量及总额。

### 5.2 对象状态

```text
pending → ready → dispatching → running
       → succeeded | failed | retryable_failed | unknown | blocked | skipped
       \→ cancel_requested → canceled | cancel_failed
```

每个对象状态迁移必须持久化时间、requestId、traceId、错误码和游戏返回。恢复规则：

1. `succeeded/failed/conflict/canceled` 不重放。
2. `ready/pending` 可派发。
3. `dispatching/running/unknown` 先按 operationId 查询或同 ID 受控重试，不能直接视为未执行。
4. `blocked/skipped` 不自动变更，人工处理需记录原因。
5. 平台重启后先恢复执行代和逐对象状态，再申请速率令牌。

### 5.3 暂停与恢复

- 暂停停止派发新 item，不中断已派发请求；已派发请求按原状态机收敛。
- 恢复前重新检查审批有效期、函数契约、预算余量、游戏健康和名单快照哈希。
- 恢复只能继续原批次；若名单、参数或预算变化，创建新批次并重新审批。
- 批次过期后不允许继续派发，剩余对象保持原状态并提示新审批。

## 6. 逐对象凭据与最终核对

1. 每个 item 均复用高风险执行契约：同 `operationId` 同请求指纹由游戏持久判重，响应丢失不重复执行。
2. 游戏 receipt、request fingerprint、结果状态和业务变更摘要必须能从批次、任务、执行日志、审计和游戏查询互相串联。
3. 最终核对分别统计：平台派发数、游戏成功数、明确失败数、结果未知数、实际发放/处置总额、游戏凭据数。
4. 对账不只比较条数：金额、币种、物品 ID、目标、批次号和结果指纹必须一致。
5. `unknown` 不能在查询窗口结束时改判失败；只能保留未知并进入人工/延长查询流程。
6. 核对报告在批次终态后生成，失败对象支持导出、复制新批次草案和引用原 operationId，但不自动继承审批。

## 7. 页面与权限

- 批量页面提供：条件编辑、预演、快照差异、审批摘要、执行进度、逐对象筛选、失败处理、核对报告。
- 审批页必须展示快照摘要、总额上限、数据源/查询时间、有效期和函数契约版本；不能只展示任务名或前端人数。
- 执行页默认只读；重试、暂停、恢复、取消、导出、补偿分别受权限控制。
- 敏感目标与参数默认脱敏；审计员可按受控路径查看完整凭据。
- 批量操作只挂载到当前 `(gameId, env)` 的发布页面，不允许跨 scope 复用执行上下文。

## 8. 验收场景

1. **故障恢复**：批次在第 37/100 对象后崩溃，重启后前 36 个凭据成功项不重放，第 37 个先查询结果，未终态后才继续，总计只发放 100 份。
2. **名单变更**：审批后增加/删除/替换任一目标或修改每人金额，执行前 blocked，需生成新快照并重新审批。
3. **逐对象核对**：游戏返回 98 成功、1 失败、1 未知；批次为部分完成，报告逐项展示 receipt/错误/查询位点，总额等于 98 份实际成功值。
4. **响应丢失**：第 50 个对象游戏已入账但响应丢失，状态为 unknown；同 operationId 重试返回原凭据并收敛成功，不重复发放。
5. **预算护栏**：游戏返回金额或数量超过审批预算，执行器立即暂停，后续对象未派发，告警包含超限 item 和已消耗预算。
6. **暂停恢复**：暂停时已派发的 5 个对象继续收敛，恢复后从第 6 个未终态对象开始，速率和并发重新受控。
7. **失败阈值**：连续资格变化达到策略阈值时批次暂停，已成功对象不被回滚，阻断对象可导出。

## 9. 待评审决策

1. 首批业务域与最大对象数、默认速率/并发/失败阈值。
2. `BatchOperation/BatchItem` 的落库形式，以及是否将逐对象事件写入 `TaskEvent` 或独立业务事件。
3. 预演结果默认有效期、游戏版本号增量校验能力与过期策略。
4. 批量重试权限归属：发起人、值班运营、审批人或管理员。
5. 补偿草案是否允许从失败/未知对象一键创建，以及二次审批摘要必须展示哪些原批次字段。
