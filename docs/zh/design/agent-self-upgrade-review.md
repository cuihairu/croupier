# Agent 自升级方案评审

日期：2026-11-28。状态：**提案待 owner 决策**。本页是 OPS-012 方案决策交付物：把
[agent-supervisor-design §10.5](agent-supervisor-design.md) 的 v0.1 草案收敛成
带推荐的决策清单，并起草两项必须达成的验收方案——**自升级失败不得砖化 agent**、
**回滚必须具备带外路径**。本页不改任何代码——实施以 owner 对下方 D1–D4 的批准为门。

## 1. 已存在的地基（代码事实）

自升级不是从零开始。2026-10-15 已落地三件互不依赖的设施（无论自升级是否实施，
它们都服务于 triage）：

| 设施                                                                                                                                                                                                  | 位置                                                          | 对自升级的作用                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------- |
| 运行实例指纹上行（`SystemInfo.agent_binary_sha256`，proto 追加，wire 兼容）                                                                                                                           | agent → `GET /ops/agents/:agentId/system-info`                | 升级前后都知道「在跑什么」             |
| 最后已知指纹锚点（注册 label `agentBinarySha256`，平台键豁免；DB `LastKnownIdentity` Unscoped 读）                                                                                                    | `agent_sessions.labels`；锚点存活于会话过期与 server 重启之后 | agent 失联（升级中断）时的 triage      |
| 受管进程更新机制（`UpdateProcess`：sha256 fail-closed pin → 停 → `.croupier-bak` 备份 → 原子换 → 起 → 5s 稳定窗 → 回滚；`update_applied`/`update_rolled_back` 事件；execlog `source=process_update`） | `internal/app/agent/ops_update.go`                            | 自升级必须改造复用的模式——不能原样照搬 |
| 授权三件套（§10.7：双开关 + allowlist fail-closed + 每次尝试都写 execlog 审计）                                                                                                                       | `allowUpdate`/`allowExec` 族                                  | 自升级加入的闸门族                     |

`UpdateProcess` 为什么不能原样复用：它的回滚假设换装后**仍有角色观察新二进制**
（agent 自己的 monitor 关闭 `waitDone` 并回滚）。自升级时该观察者就是被替换的
进程本身——agent 头上没有东西。自升级失败 = 失联，因此不变量是：

> **自升级失败的最坏结局是 agent 以旧版本重启——绝不是砖死、无法再拉起。**

## 2. 四问（§10.5 推荐，供签核）

### D1 — 升级源

| 选项 | 形态                                                                       | 后果                                     |
| ---- | -------------------------------------------------------------------------- | ---------------------------------------- |
| (a)  | server 侧 staged 中继（server 收包暂存后分发；同 §10.4 `stagedPath` 形态） | 复用既有 wire+审计面；不引入第二条信任链 |
| (b)  | agent 直取外部 URL                                                         | 需自建 TLS+签名信任链                    |
| (c)  | 配置版本钉版（server 下发 `targetVersion`，agent 自取）                    | 信任决策分散；更难审计                   |

**推荐 (a)**：升级面天然被授权与审计面覆盖（§10.7 三件套）；给系统中最高危的
动作引入第二条信任链是错误的取舍。

### D2 — 触发模式

| 选项 | 形态                                                     | 后果                                     |
| ---- | -------------------------------------------------------- | ---------------------------------------- |
| (a)  | 手动 API，`allowUpdate` 旁独立键（如 `allowSelfUpdate`） | 显式、可审计、无静默升级                 |
| (b)  | ConfigVersion 热更携带升级字段                           | 升级随配置静默发生——对此风险等级不可接受 |
| (c)  | §10.6 cron 调度                                          | 维护窗口可期，但缺省即静默               |

**推荐先做 (a)**：自升级是系统最高危动作，绝不允许随配置静默触发；批量升级在
(a) 之上叠批量编排（运营驱动），不另设触发源。

### D3 — 重启接力（核心难点）

agent 必须在持有控制连接的同时替换自己正在运行的二进制。选项：

| 选项 | 形态                                                                | 后果                                                                                     |
| ---- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| (a)  | 外部 supervisor 重新拉起（systemd/k8s 对退出即重启）                | 依赖部署面保证退出即重启                                                                 |
| (b)  | fork+exec 接力（fork 子进程等待换装完成后 exec 新路径；父进程退出） | 无 supervisor 也自洽；有 supervisor 时父退出自然退化为退出重启——两种部署形态一条代码路径 |
| (c)  | 双进程轮替（影子进程）                                              | 复杂度最高；双活 agent 对受管进程有脑裂风险                                              |

**推荐 (b)**：裸主机（无 supervisor）上自升级依然自洽；systemd/k8s 下父进程退出
触发既有重启策略，新二进制以任一路径起来。重连走既有注册路径刷新指纹 label+锚点
（§1），换装前后「在跑哪个版本」始终可查。

### D4 — 失败姿态与回滚

自升级失败 = 失联；回滚只能是带外的。设计约束（承 §10.5）：

1. 旧二进制**改名备份、绝不删除**（同 §10.4 `.croupier-bak` 的 last-known-good 语义）。
2. 新版本必须**活过稳定性窗口**才宣告成功——自升级建议比受管进程 5s 缺省更长
   （agent 头上没有外部观察者；窗口是旧二进制成为回滚目标前唯一的自证健康闸）。
   具体取值：**10s，配置门控**。
3. 窗口内死亡 = supervisor 按既有策略重启（备份还在 → 旧版本回归），或人工带外介入。
4. 指纹记录沿 §10.4 三落点：事件闭集新增 `self_upgrade_applied` /
   `self_upgrade_rolled_back` + execlog 审计 `source=agent_self_upgrade` + report 面。

## 3. 验收方案（实施的验证基准）

### A1 — 自升级失败不砖化（必须达成）

| 场景                                | 期望                                                                                         |
| ----------------------------------- | -------------------------------------------------------------------------------------------- |
| 新二进制在稳定性窗口内退出          | `.croupier-bak` 备份仍在 → supervisor/人工拉起跑**旧**版本；agent 重连并以**旧**指纹重新注册 |
| 新二进制在窗口后失败（运行态失败）  | 按既有恢复语义处理；`.croupier-bak` 保留供人工回滚                                           |
| staged 内容 hash 不匹配             | 不触碰运行中二进制即拒绝（fail-closed pin，§10.4 第一道闸）                                  |
| 换装中途安装失败（EXDEV/权限/磁盘） | 旧二进制原封不动；execlog 留显式失败记录；agent 继续运行                                     |
| 首次安装（无旧版本可回滚）          | 无回滚目标：显式无事件边界（适用 §10.4 诚实边界④）；execlog 即记录                           |

### A2 — 带外回滚真实可用（必须达成）

- 备份路径确定（`<target>.croupier-bak`，同目录），人工（或 runbook 脚本）
  不依赖平台工具即可恢复。
- DB 最后已知指纹锚点（§1）让运营在 agent 失联时也能确认「最后已知在跑哪个版本」。
- 经备份回滚是显式文档化的 runbook 步骤，不是未记载的内部细节。

### A3 — 换装全程可观测

- 每次尝试（成功/业务失败/agent 不可达）都留 execlog 记录
  （`source=agent_self_upgrade`），按 (agentID, 时间, 旧→新指纹) 与事件流对齐。
- server 侧 metrics-stale 告警区分「agent 升级中」与「agent 失联」（§10.5 已知
  边界③）——v1 至少经 execlog 在途记录区分；专用「升级中」状态不在 v1 范围。

## 4. 已知边界（承 §10.5，不变）

- Windows 无 `fork`——D3(b) 在该平台需自己的方案（子进程 spawn + 等待）。
- 多 agent 批量升级排序（先备后主、分批）是编排层工作，不属于单 agent 原语。
- 自升级期间该 agent 全部受管程序共享盲窗（恢复循环/探测随 agent 一起停）。
