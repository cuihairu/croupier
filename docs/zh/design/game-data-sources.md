## 1. 需求：骨架首适配器需要什么数据

§5.5 三层（内核 / 协议适配骨架 / 每游戏适配器）中，骨架要能把一个真实游戏的玩家侧登录/握手/存活探测表达成声明式 steps，需要的输入是：

- 连接建立序列（地址/端口/传输层 TCP 或 UDP、初始握手包结构）；
- 帧格式（长度前缀/varint/对齐）、压缩与加密协商；
- 认证流程（若需）与「存活即可判定」的最小交互；
- 按游戏版本漂移的版本化管理。

本仓无任何游戏协议栈可复用（`sdks/` 是游戏服务器→agent 注册面），数据必须外取。候选按用户裁定从**现成开源项目**收集，不自建采集/逆向。

## 3. 单一推荐与理由

**推荐 PrismarineJS/minecraft-data，首个适配器目标 = Minecraft Java 版 offline-mode 自托管服务端。**

理由：

1. **唯一 MIT**：三候选中唯一同时允许商用与二次分发（附版权声明），是唯一能走「数据直接消费」通道的源；其余只能走「事实参考」通道（见 §4）。选型代决在授权范围内，不触碰 License 变更确认线。
2. **机器可读 + 按版本版本化**：`protocol.json`（状态机 + 包结构 + 字段类型）可脚本转换成 §5.5 声明式 steps，不需要人肉从 C++/Java 源码扒协议——「数据源从网络收集」的最低成本路径，且版本漂移管理有现成结构。
3. **真实商业游戏、协议形态代表性足**：Minecraft 是真实商业游戏（自托管副本做测试靶，**非 mock**）；Java 版 TCP varint 帧 + zlib 压缩 + 在线加密握手是端游/长连接手游的主流形态，Bedrock（RakNet/UDP）覆盖 UDP 族——两个协议族代表「各种类型游戏」的样本深度。
4. **零账号 E2E**：offline-mode 不校验 Microsoft 账号，docker 自托管服务端即可玩家视角全链路验证（登录握手→存活判定），满足「先骨架+一个真实游戏适配器」且不被账号卡住；在线加密链单独标待账号验证（§6）。

Luanti 记为 **UDP 族第二候选**（全开游戏、法律最干净，官方文档质量高），但本轮只做一个适配器（用户已决），且其文档是人读散文而非机器可读，转换成本高于 minecraft-data。AzerothCore/TrinityCore 定位 **L3 商业 MMO 知识原型**（登录加密/包结构的深度参考），不作首适配器。

## 5. 接入方式

**以其为参考自建适配器骨架；minecraft-data 走工具化数据通道。** 两者并行不矛盾：

1. **骨架**（Apache-2.0 自研，§5.5 三层）：声明式 steps DSL + 「协议未接入」一等状态（不伪装成已接入，不写空实现）。**已交付（2026-10-15）**：`core/healthprobe/protocol.go`（L2）+ minecraft 首适配器（L3），交付记录见 agent-health-recovery-review.md §5.5.6。
2. **首适配器**（Minecraft Java offline-mode）：**实际落地为 SLP（Server List Ping）L3 代码适配器，按公开协议规范自写**——SLP 只有握手+两包交互，不需要 `protocol.json` 字段级数据，构建期拉取通道**留给登录级 L3**（登录握手/Login 流程才需要字段级协议表达，届时按本节原方案走 minecraft-data 工具化通道，原始 json 仍不入库）。零账号验证 offline/online-mode 服务器均可用（SLP 不涉登录加密）；online-mode 的**登录链**验证仍按 §6 待账号。
3. **自托管验证**：docker 起 vanilla 服务端 offline-mode（EULA 一次接受，仅内网测试），玩家视角拨测零账号闭环。
4. **L3 商业游戏**（后续）：以开源服务端实现为知识原型（零拷贝），真实协议接入按「游戏方提供知识 or 玩家侧账号实测」双路走，随每游戏立项单独定。
