## 核心主张

探测体系应统一为**一个可复用的探测内核**，而不是 Agent 与 Server 各实现一套探活逻辑。分三层：

1. **探测内核共用**：统一探测接口、调度、超时、连续失败阈值、恢复判定、状态机、事件模型。
2. **探测器按协议扩展**：HTTP、TCP、数据库，以及**模拟游戏客户端的协议探测**，各自实现探测逻辑。
3. **执行位置由探测目标决定**：Agent 与 Server 都可运行同一内核，但跑在哪，取决于探测结果代表**谁的视角**、网络位置是否影响结论。

明确强调：**共用探测代码 ≠ 所有探测由同一端执行，也不等于 Server 与 Agent 探测相同目标。**

### 为什么游戏协议探测不能用 TCP 代替

TCP 端口连通，不代表游戏服务器真的能接受客户端登录、进入游戏或完成关键协议交互。因此它与普通 HTTP/TCP 探测**不在同一层次**：TCP 成功只说明连接建立成功；模拟客户端还可继续验证协议握手、登录响应、角色进入等业务流程。**具体探到哪一步由游戏协议与场景定义，不应强行让所有游戏共用同一流程。**

三个易混淆的层次：游戏服务器存活 ≠ 游戏服务可用 ≠ 玩家所在网络可正常访问。

## 1. 代码归属建议

原文明确「不建议再创建第二套健康探测引擎，而是扩展现有的公共能力」，公共包只放通用机制。

| 代码职责                       | 建议归属                 | 说明                                   |
| ------------------------------ | ------------------------ | -------------------------------------- |
| `Checker`、超时、调度          | `core/healthprobe`       | Agent、Server 共用                     |
| 连续失败阈值、恢复阈值、状态机 | `core/healthprobe`       | 避免两套状态判定逻辑                   |
| 故障窗口、恢复事件、时间线     | `core/healthprobe`       | 统一事件语义                           |
| HTTP、TCP 探测器               | 公共探测器包             | 谁需要谁就实例化                       |
| 数据库探测器                   | 公共探测器包或独立适配包 | 是否执行由部署位置决定                 |
| 游戏客户端模拟探测器           | 独立的游戏协议适配模块   | 复用公共接口，避免游戏协议依赖污染内核 |
| 探测目标配置与下发             | Server                   | 管理配置、版本、授权与执行位置         |
| 探测执行、结果采集             | Agent 或 Server Runtime  | 按目标的网络视角执行                   |

游戏模拟探测模块**必须实现已有 `Checker` 契约**，只返回探测结果，不自行再实现失败阈值、状态机和故障窗口。

## 2. Agent / Server 分工表

判断标准：**探测结果要回答什么问题**为第一标准，再结合网络可达性决定执行位置。

| 探测对象                                 | 默认执行位置                               | 原因                                 |
| ---------------------------------------- | ------------------------------------------ | ------------------------------------ |
| 游戏进程是否存活                         | 游戏所在节点的 Agent                       | 本地进程状态最准确                   |
| 游戏端口、内部服务是否可达               | 能访问该内网的 Agent                       | Server 可能无法进入游戏内网          |
| 模拟真实客户端登录、握手、进入游戏       | 专用探测 Agent，或具备对应网络位置的 Agent | 必须验证协议链路，而非只看端口       |
| 面向玩家的跨网络游戏可达性               | 部署在代表性网络位置的探测 Agent           | 单一机房探测不能代表玩家侧网络       |
| Server 自身依赖的数据库、Redis、内部 API | Server                                     | 验证平台自身运行条件                 |
| 只有 Server 能访问的第三方平台 API       | Server                                     | Agent 无法代表 Server 的实际访问路径 |
| 只有游戏内网能访问的第三方服务           | 对应内网 Agent                             | Server 的探测结论不具代表性          |

## 3. 五条设计约束（须写进设计文档）

1. **共用引擎，不共用执行位置** —— Agent 与 Server 调用同一内核，但每个探测目标都要声明期望的网络视角与执行位置。
2. **探测与恢复分离** —— 探测器只观测并返回结果；是否重启进程、执行恢复脚本由独立的恢复策略决定；**外部服务探测失败不能默认触发本地进程重启**。
3. **配置与执行分离** —— Server 负责配置、授权与分发；实际探测在选定的 Agent 或 Server 上执行，上报结果须带目标标识、执行位置、时间、探测类型。
4. **游戏模拟探测独立演进** —— 不把具体游戏协议写进 `core/healthprobe`；不同游戏提供不同协议适配器，共享探测生命周期与结果语义。
5. **避免重复探测与重复告警** —— 同一目标可有多个探测位置，但必须区分各探测点结果，由 Server 汇总；**不能把某个 Agent 的失败直接认定为游戏全局故障**。

## 4. 对本仓现有设计的五点修正建议

1. 把游戏客户端模拟探测 Agent 纳入正式架构、配置模型与 TODO。
2. 定义 `ProbeTarget` 的执行位置、探测视角、探测类型、协议适配器与超时策略。
3. 确定探测结果从 Agent 上报 Server 后，如何进入统一的健康状态、告警与恢复流程。
4. 明确 Server 侧现有数据库等探测哪些留在 Server、哪些因网络可达性或目标视角迁到 Agent。
5. 检查 Windows 进程探测等现有实现的跨平台准确性，避免只统一接口却留下底层错误。
